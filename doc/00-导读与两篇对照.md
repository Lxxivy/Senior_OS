## 2. 两篇是什么关系

一句话：**一篇讲"纵向的系统底座"，一篇讲"横向的协作语义"。**

```
        ┌─────────────────────────────────────────────┐
        │  论文二：多个 agent 之间怎么组织、怎么通信    │   ← 协作语义层
        │  actors / types / structures / strategies    │
        │  / coordination protocols                    │
        └───────────────────┬─────────────────────────┘
                            │ 运行在
        ┌───────────────────┴─────────────────────────┐
        │  论文一：多个 agent 共享一套模型与工具时      │   ← 系统资源层
        │  谁先跑、上下文怎么切、内存怎么管、权限谁批    │
        └─────────────────────────────────────────────┘
```

- 论文二回答"**该怎么组织**"：辩论（竞争）、角色分工（合作）、分层汇报（结构）、规则驱动还是模型驱动（策略）。
- 论文一回答"**底层扛不扛得住**"：这些协作模式一旦真的跑起来，几十个 agent 同时调同一个模型，排队、超时、上下文串味、工具冲突、越权操作怎么解决。
- 两者结合的现实含义：**协作拓扑设计得再漂亮，没有调度和隔离，规模一上去就会退化**；反过来，内核再高效，若协作协议设计糟糕，多智能体也会输给一个提示词写得好的单 agent——这正是论文二明确写下的教训（"次优设计的 MAS 会被强提示的单 agent 反超"）。

## 3. 关键结论对照

| 议题 | 论文一的立场 | 论文二的立场 |
| --- | --- | --- |
| 多 agent 一定更好吗 | 不预设；但给了"同等硬件下吞吐 ×2.1、成功率不掉"的工程证据 | 不一定：有效的协作通道才带来增益，设计不佳反而更差 |
| 瓶颈在哪 | 资源竞争与调度缺失（LLM 推理是长耗时系统调用） | 协调成本、角色/协议设计、可评估性 |
| 怎么提升 | 内核化：调度器、上下文快照与恢复、内存/存储、工具、访问控制 | 结构化：明确协作类型、拓扑、策略与终止条件 |
| 评估方式 | 成功率（HumanEval/MINT/GAIA/SWE-Bench-Lite）+ 吞吐 + 延迟 + 并发扩展 | 成功率、任务产出、成本效益、协作效率；并指出基准缺失是开放问题 |
| 对工程的要求 | 提供 SDK，让 ReAct/Reflexion/AutoGen/Open-Interpreter/MetaGPT 免改代码接入 | 提供框架（AutoGen、CAMEL、crewAI 等）与设计经验法则 |

## 5. 名词速查

| 术语 | 含义 | 出处 |
| --- | --- | --- |
| Agent / 智能体 | 由 LLM 驱动、能规划并使用工具完成任务的程序实体 | 两篇 |
| MAS（Multi-Agent System） | 多个智能体通过通信与协调共同完成任务的系统 | 论文二 |
| AIOS Kernel | 把 LLM 实例、工具、内存等抽象为内核资源并提供系统调用的中间层 | 论文一 |
| LLM Core | 把每个 LLM 实例封装成类似 CPU 核的处理单元，统一接口 | 论文一 |
| Context Switch / 上下文切换 | 推理中途挂起并保存状态（文本级或 logits 级），稍后恢复继续生成 | 论文一 |
| Collaboration Channel / 协作通道 | 一组 agent 之间的协作配置：参与者 + 类型 + 结构 + 策略 | 论文二 |
| Cooperation / Competition / Coopetition | 合作 / 竞争 / 竞合 | 论文二 |
| Coordination Protocol / 协调协议 | 规定谁在何时说什么、何时终止的规则 | 论文二 |
| Artificial Collective Intelligence | 人工集体智能，多智能体研究的长期目标 | 论文二 |
