## §0 一页速览

**先给结论，后面全是证据。**

| # | 结论 | 证据位置 |
|---|---|---|
| 1 | 赛题的 20% 目标本质是**应用层并发 + 资源容量**问题，不是"挑一个更强的排序算法"问题。9 节点演示中并发本身拿到 1.55×，三种排序策略的 makespan 差异 ≤0.5% | §4.4、§4.2 E1 |
| 2 | 排序算法的价值不在平均 makespan，而在**尾部延迟**：单槽位重压下，SPT 的 p90 等待 12.1s、FIFO 14.8s、CP 19.2s，差 1.6 倍 | §4.2 E2 |

| 6 | 槽位饱和后加机器无收益：W3 负载 3 槽 36.0s ≈ 4 槽 35.7s ≈ 6 槽 35.7s，下界就是关键路径 | §4.2 E4 |

## §1 问题形式化

### 1.1 调度问题的五元组

一个多智能体任务执行过程可以写成：

```
S = (V, E, w, R, m)
```

- `V`：子任务集合，`|V| = n`；
- `E ⊆ V×V`：依赖边，`(u,v)∈E` 表示 v 必须在 u 完成后才能开始；
- `w: V → R+`：每个子任务的耗时（LLM 推理 / 工具调用 / IO，量级差两个数量级）；
- `R = {llm, tool, io}`：资源类别；
- `m: R → N+`：每类资源的并发槽位数（端侧通常 llm=1~2、tool=1~2、io 不受限）。

目标是找**开始时间分配** `s: V → R+` 与资源占用，使：

```
minimize   makespan = max_{v∈V} (s(v) + w(v))
subject to s(v) ≥ s(u) + w(u)      ∀(u,v)∈E
           同一时刻占用某类资源 r 的任务数 ≤ m(r)
```

这是经典的**不可抢占、带资源约束的 DAG 调度**（RCPSP 的特例）。三件事一起决定了它很难：

1. **NP-hard**：即使 `m(·)=∞`，最小化 makespan 等价于同构多机调度（P||Cmax），已是 NP-hard，只能近似。
2. **不可抢占**：LLM 调用不能"半途换任务"，正在生成的内容没法挂起让路（vLLM 的抢占是算子级、对应用透明，见 §3）。
3. **估算误差**：`w` 只能估。7B 模型下同一个 prompt 的耗时可能因缓存前缀命中与否差 2–3 倍（[doc/08 §4](08-评测基准与端侧推理加速-精读.md)），所以任何依赖精确 `w` 的排序都要有鲁棒性兜底。

### 1.2 三个下界（用来判断"还有多少空间"）

| 下界 | 公式 | 演示 DAG 的值（9 节点） |
|---|---|---|
| 关键路径 | `CP = max_{path} Σ w` | 3.80s |
| 资源总量 | `max_r (Σ_{v∈V_r} w(v) / m(r))` | llm: 4.6/2=2.30s；tool: 2.4/1=2.40s |
| 理论最优 | `OPT ≥ max(CP, 各资源下界)` | ≥3.80s |

实测 4.50s，**达到下界的 84%**；差额 0.70s 来自 `tool=1` 的串行段与 LLM 批处理空转。想把 20% 变成 30–40%，靠的就是把这些差额再吃掉（§6 的批填充与回填）。

### 1.3 与赛题指标的换算

赛题要求"总时间减少 ≥20%"，等价于：

```
T_parallel ≤ 0.8 × T_serial  ⇔  speedup ≥ 1.25×
```

本文所有加速比统一以**同 DAG、同任务集、同 warm-up 的串行执行**为基线，口径与 [doc/03 §6.2](03-赛题对标与多智能体系统设计方案.md) 一致：wall-clock、预热 ≥3 轮、取中位数、报 p90，禁止拿"去掉串行依赖后的理想时间"当基线。

## §2 经典调度算法目录

> 说明：本节算法属于操作系统/并行计算教材级内容（Graham 1969、Topcuoglu HEFT 2002 等），本次未下载原文复核，只作选型参考，不引用具体实验数字。

### 2.1 单机/单资源队列类

| 算法 | 规则 | 优点 | 缺点 | 多智能体里的对应物 |
|---|---|---|---|---|
| **FCFS/FIFO** | 先到先服务 | 简单、公平、无饥饿（不插队） | 大任务堵队头（convoy effect） | AIOS 默认行为；多数框架的"按提交顺序跑" |
| **SJF / SPT** | 最短作业优先 | 平均等待最优（可证明） | 长任务饥饿；需预知时长 | 短报告/校验优先；与"先摘低垂果实"直觉一致 |
| **LPT** | 最长作业优先 | 多机近似比好（4/3−1/(3m)） | 单机平均等待差 | 大 LLM 调用先占槽，减少尾部 |
| **优先级/EDF** | 截止期或用户优先级 | 可表达 SLA | 需要可信的截止期 | 赛题演示里给"关键路径上的节点"高优先级 |
| **RR** | 时间片轮转 | 交互公平 | 上下文切换开销；对 LLM 无意义 | AIOS 的 RRScheduler（有 bug，见 §5） |

### 2.2 DAG/多机类

| 算法 | 思想 | 近似保证 | 适用 |
|---|---|---|---|
| **List scheduling（含 HEFT）** | 按优先级依次把任务塞给最早空闲的槽位 | 同构机下 ≤ (2−1/m)·OPT | 通用主力；本文默认策略 |
| **关键路径优先（CP）** | bottom-level 大者先跑 | 见上（CP 是 list scheduling 的一种优先级） | 分支多、路径长尾明显的负载 |
| **HEFT** | 优先级=向上秩，选"最早完成时间"的机器 | 异构机经典启发式 | 资源异构（端侧 CPU/GPU/NPU）时最该用 |
| **工作窃取** | 空闲线程从别人队列尾部偷活 | 负载均衡好 | 运行时任务数远大于槽位时 |
| **回填（backfilling）** | 小任务插到大任务的预留空档 | 提升利用率 | 批处理 + 长任务混合 |

### 2.3 选型结论

1. **别一上来就上 HEFT**：HEFT 需要"每个任务在每种资源上的耗时"矩阵，7B 端侧估不准，收益被误差吃掉（§4.2 E1 里 HEFT 与 CP 只差 0.06×）。
2. **CP + FIFO 兜底**是最稳组合：CP 负责压尾部，FIFO 负责无饥饿与可解释。
3. **SPT 只在"交互型 + 单槽位"场景值得开**：它把 p90 等待压下来（§4.2 E2），代价是长任务可能等很久——演示场景可接受，离线跑批不可接受。

## §3 LLM/Agent 系统的调度特殊性

传统调度假设任务耗时稳定、资源同质。LLM 系统三条都不成立。

### 3.1 推理引擎本身就在调度

| 机制 | 效果（来自已下载论文，见 doc/04/doc/08） | 对应用层调度的影响 |
|---|---|---|
| **PagedAttention / 连续批处理**（vLLM） | KV 显存有效利用率 8.9%→96.3%，吞吐 2–4× | 同一个 batch 里塞更多请求，延迟略升、吞吐大升 |
| **前缀缓存 / RadixAttention**（SGLang） | 共享前缀 1.67×/3.58×；整体吞吐 6.4×、延迟 3.7×、JSON 解码 1.6× | 同 system prompt、同角色的任务应尽量相邻提交 |
| **应用层流水线**（Parrot） | LLM 应用 30–50% 时间花在推理引擎之外（最坏 >70%）；语义变量暴露 DAG，性能目标反向传播；该机制单独 2.35×、MetaGPT 负载最高 11.7× | **这才是应用层调度的最大金矿**：把引擎外的等待（工具、校验、拼 prompt）与引擎内推理重叠 |

**推论**：如果我们的调度器只把 LLM 请求排个序丢给内核，加速上限由推理引擎决定（约 2–4×，取决于 batch）；如果同时把 tool/IO 任务与 LLM 重叠，才能逼近关键路径下界。Parrot 的 11.7× 正是"引擎外 30–70% 被并行掉"的结果。

### 3.2 AIOS 内核的现实

（源码事实，详见 §5）内核把请求分四类、各自一个线程；LLM 每 `batch_interval` 攒一批；非 LLM 请求**一个线程串行**处理。这意味着：

- 应用层提交 5 个 LLM 请求 → 内核攒批 → 一次 batch 推理，吞吐友好；
- 应用层提交 5 个 tool 调用 → 内核串行执行，**即使彼此独立也无法并行**；
- 依赖关系内核完全不知道 → `syscall.join()` 把"提交"变成"等待"，一旦应用层按串行代码写，就退化成串行。

### 3.3 端侧 7B 的五条硬约束

| 约束 | 数据 | 调度取向 |
|---|---|---|
| 模型慢、槽位少 | 7B 在消费级 GPU 上单请求数十 token/s；并发 2 以上显存吃紧 | LLM 槽位设 1–2，宁可让 tool/IO 多并行 |
| 前缀缓存命中率决定延迟 | 共享前缀 1.67–3.58×（SGLang） | 同角色任务连续提交，别交错换 system prompt |
| 工具调用能力弱 | AgentBench：6B 模型 OA=0.11，≤70B 均值 0.51（doc/08 §1） | 工具调用要少而确定，调度别依赖"模型自己挑工具" |
| 长上下文成本高 | MemGPT 式分页、token 预算 | 子任务粒度别太碎（每次调用都带上下文） |
| 估算不准 | 缓存命中与否 2–3× 差 | 排序策略要能容忍 w 误差：CP 用拓扑结构而非绝对耗时，天然更鲁棒 |

## §4 实验

### 4.1 实验设置

| 项 | 设置 |
|---|---|
| 模拟器 | `build/sched_sim2.py`（30 seeds，结果 `build/sched_results.json`，原始输出 `build/sched_out.txt`） |
| 负载 | W1 看板 6 节点（浅）；W2 分析 12 节点（中）；W3 分层 20 节点（深）；W4 重尾异构（个别 llm 任务 5–8s） |
| 策略 | fifo、spt、lpt、cp（关键路径）、heft、rand（随机） |
| 资源 | 默认 llm=2 / tool=1 / io=2；E2 收紧到 1/1/1；E4 做槽位扫描 |
| 真实线程 | `build/sched_demo_threads.py`（真 sleep + Semaphore，9 节点，3 次平均） |
| 原型 | `src/scheduler.py` + `src/demo_scheduler.py`（5 个假 agent，9 节点，3 次平均） |

### 4.2 E1 策略矩阵（30 seeds，加速比 vs 串行）

| 负载 | fifo | spt | lpt | **cp** | heft | rand |
|---|---|---|---|---|---|---|
| W1 看板 6 节点 | 1.69 | 1.69 | 1.69 | 1.69 | 1.69 | 1.69 |
| W2 分析 12 节点 | 1.60 | 1.57 | 1.62 | **1.62** | 1.62 | 1.58 |
| W3 分层 20 节点 | 2.73 | 2.63 | 2.55 | **2.82** | 2.76 | 2.68 |
| W4 重尾异构 | 1.40 | 1.36 | 1.40 | **1.40** | 1.40 | 1.37 |

**读法**：
- W1 六个策略完全一样——**依赖结构决定并行度时，排序毫无用武之地**。这直接解释了为什么"接了并发就有 1.69×"。
- W3 上 CP 比 LPT 高 0.27×（约 10%），是排序能贡献的最大区间。
- W4 全员 1.40：重尾任务卡住关键路径，排序改不动。

### 4.3 E2 单槽位收紧（llm=1、tool=1、io=1）

| 负载/策略 | makespan 加速 | p90 等待 |
|---|---|---|
| W3 cp | 1.52 | 19.2s |
| W3 fifo | 1.52 | 14.8s |
| W3 heft | 1.51 | — |
| W3 rand | 1.47 | — |
| W3 spt | 1.47 | **12.1s** |
| W4 全策略 | 1.20 | — |

**读法**：槽位收紧后平均 makespan 全被压到 1.2–1.5×，策略差异只剩 3–4%；但 p90 等待差 1.6 倍（19.2s vs 12.1s）。**赛题若只报总时间，排序收益很小；若评委追问"最慢的用户等多久"，SPT/CP 的价值才显现。**

### 4.4 E3 AIOS 原生 vs 应用层调度

设 AIOS 原生 = 1s 攒批 + 0.4s 固定开销 + FIFO；应用层 = 立即派发 + HEFT。

| 负载 | 串行 | 原生 | 应用层 | 原生加速 | 应用层加速 | 额外收益 |
|---|---|---|---|---|---|---|
| W1 | 35.4s | 24.2s | 20.9s | 1.46× | **1.69×** | 1.16× |
| W2 | 78.6s | 52.8s | 48.5s | 1.49× | **1.62×** | 1.09× |
| W3 | 105.1s | 44.5s | 38.3s | 2.36× | **2.74×** | 1.16× |
| W4 | 96.4s | 71.8s | 69.0s | 1.34× | **1.40×** | 1.04× |

**读法**：只用内核批处理也能拿 1.34–2.36×（因为批处理本身就把串行夸大了的延迟摊薄了），应用层再调度能多 4–16%。这个 1.04–1.16× 就是"应用层 TSU"的净价值，也是答辩时可以主张的增量。

### 4.5 E4 槽位扫描（W3、CP、摊薄）

| 槽位配置 | makespan |
|---|---|
| 1 | 81.3s |
| 2 | 42.6s |
| 3 | 36.0s |
| 4 | 35.7s |
| 6 | 35.7s |

**读法**：3 槽即饱和，之后加槽位无收益——**这是关键路径下界的直接体现**。演示/答辩要把资源配到这个拐点，别让评委看到"加了机器不提速"的尴尬。

### 4.6 真实线程演示（9 节点，真 sleep）

| 策略 | makespan | 加速 | p90 等待 |
|---|---|---|---|
| serial（拓扑序串行） | 7.00s | 1.00× | 2.20s |
| naive_fifo（无依赖、起线程就发） | 4.60s | 1.52× | ~0 |
| dispatch_fifo（依赖门控 + FIFO） | 4.61s | 1.52× | ~0 |
| dispatch_cp（依赖门控 + 关键路径） | 4.62s | 1.52× | ~0 |

**读法**（诚实结论）：一旦依赖门控正确，三种派发策略都是 1.52×——**排序在这个粒度下没有可测差异**，因为 tool=1 已经饱和、关键路径 3.8s 主导。想看见排序差异，需要更多同类资源竞争（E1/E2 的模拟就是干这个的）。

### 4.7 原型演示（`src/demo_scheduler.py`，9 节点、5 个假 agent）

```
任务数=9  串行基线(理论)=7.0s  资源槽位=llm:2 tool:1 io:2
fifo             makespan=4.50s  speedup=1.55×
critical_path    makespan=4.50s  speedup=1.55×
spt              makespan=4.51s  speedup=1.55×
```

达到 §1.2 下界 3.80s 的 84%。三种策略差异在测量噪声内（±0.01s），与 §4.6 一致。

**资源容量 × 策略矩阵**（`build/demo_matrix.py`，5 次取中位数；串行基线 7.0s）：

| 槽位 llm/tool/io | fifo | critical_path | spt | lpt |
|---|---|---|---|---|
| 1 / 1 / 1 | 4.70s（1.49×） | 4.70s（1.49×） | **5.51s（1.27×）** | 4.70s（1.49×） |
| 2 / 1 / 2 | 4.50s（1.55×） | 4.50s（1.55×） | 4.50s（1.55×） | 4.50s（1.55×） |
| 2 / 2 / 2 | **3.70s（1.89×）** | 3.70s（1.89×） | 3.70s（1.89×） | 3.70s（1.89×） |
| 4 / 2 / 2 | 3.70s（1.89×） | 3.70s（1.89×） | 3.70s（1.89×） | 3.70s（1.89×） |
| 8 / 4 / 2 | 3.70s（1.89×） | 3.70s（1.89×） | 3.70s（1.89×） | 3.70s（1.89×） |

**这张表是全文最重要的证据**：
1. **容量 > 排序**：把 tool 槽位从 1 加到 2，1.55× → 1.89×（+22%）；继续加 llm 槽位（4、8）毫无收益——瓶颈是 `tool=1` 的串行段，不是 LLM。这与 §1.2 下界、§4.5 槽位扫描完全一致。
2. **排序在容量充足时完全失效**（后三行四种策略同值），因为此时 makespan = 关键路径 3.7s，所有决策都被依赖结构钉死。
3. **SPT 在紧配置下会变坏**：1/1/1 时 SPT 5.51s（1.27×），比其他策略慢 17%。原因是它优先跑 0.3–0.4s 的 schema/docs 小任务，把 1.2s 的 backend 往后推，而 backend 在关键路径上——**SPT 优化的是平均等待，牺牲的是 makespan**。这反证了"排序必须看关键路径，而不是只按耗时"。
4. 3.70s 略低于估算的关键路径 3.80s，是 `estimate_s` 与实际 `sleep` 的细微差异，不影响结论。

**给赛题的直接建议**：先保证依赖门控正确 + tool 侧并行（应用层自己用线程跑工具，因为内核 tool 队列是单线程），再谈排序；演示时把资源配到 2/2/2 这个拐点，能稳定拿 1.85–1.90×。

### 4.8 口径与局限（必须写进答辩材料）

1. **假任务**：演示 agent 用 `time.sleep`，不含真实推理；数字只能证明"调度器逻辑正确 + 结构上能到多少"，不能直接当 7B 实测。
2. **GIL**：Python 线程对 CPU 密集无效；LLM 调用是"释放 GIL 的阻塞 IO"，所以线程模型对 LLM/工具场景成立，对本地 CPU 重算（本地 embedding）不成立。
3. **模拟器耗时是参数**：E1–E4 的价值是"策略相对优劣"，不是绝对秒数。
4. **批处理干扰**：AIOS 的 1s 攒批会让"小任务先跑"产生不可预测的等待，实验里显式建模了 0.4s 开销，真实值需实测校准。
5. **单机**：未测多机/多卡；端侧真实场景还要考虑显存不足导致的 OOM 降级。

## §5 映射到 AIOS 内核：为什么必须在应用层调度

### 5.1 内核做了什么（源码事实）

| 事实 | 位置 | 后果 |
|---|---|---|
| 四类队列：llm / memory / storage / tool | `aios/hooks/stores/_global.py:11-37` | 类型隔离，跨类型可并行 |
| LLM 每 `batch_interval` 攒批 drain | `aios/scheduler/fifo_scheduler.py:206-235`（默认 1.0s，`:70`） | 小请求被迫等批；单请求延迟 = 排队 + 批内推理 |
| 非 LLM 各只有 1 个处理线程，FIFO 逐个执行 | `fifo_scheduler.py:237-314`、`base.py:89-108` | 独立 tool 调用无法并行 |
| 提交即同步等待 | `aios/syscall/syscall.py:185-186`（`start()` + `join()`） | 应用层串行写法 → 全串行 |
| 无优先级、无依赖、无抢占、无全局并发上限 | 全文件 | DAG 语义只能由应用层实现 |
| RR 调度器有 bug | `rr_scheduler.py:180-181`（单对象传给批量函数，必 TypeError） | 只能用 FIFO；`use_context_manager:false` |

### 5.2 应用层必须补的四件事

1. **依赖门控**：维护 DAG 的入度，前驱全部完成才提交下游（内核不会帮你等）。
2. **资源分类配额**：给 llm/tool/io 各自限并发；tool 尽量在应用层自己并行（因为内核 tool 队列是单线程）。
3. **优先级**：用 bottom-level（关键路径）排序就绪队列，而不是提交顺序。
4. **观测**：利用内核返回的 `waiting_times`/`turnaround_times`（`syscall.py:198-214`）算等待占比，作为调参依据。

### 5.3 端侧推荐配置（结合 §3.3）

```yaml
# aios/config/config.yaml 关键项
use_context_manager: false        # RR 有 bug，必须关
scheduler: fifo                   # 只用 FIFO
batch_interval: 0.2               # 默认 1.0s 对交互演示太长，改小
agent_factory:
  max_workers: 4                  # 默认 64 在 7B 端侧反而造成排队抖动
llms:
  models: [{name: qwen2.5-7b-instruct, backend: vllm, hostname: localhost:8001}]
```

配合应用层参数：`llm=1~2`、`tool=2~4`、`io=4`，`batch_interval` 从 0.2s 起调、以等待占比 <15% 为目标。

## §6 落地算法：CP-RA

> Critical-Path + Resource-Aware，即"关键路径优先 + 资源感知准入 + 批填充 + 回填"。

```text
输入: DAG(V,E,w), 槽位 m={llm:2, tool:4, io:4}, 就绪队列 Q, 运行中集合 R
输出: 调度序列

1  计算每个节点 bottom-level: bl(v) = w(v) + max_{v→u} bl(u)      # 反向拓扑一遍
2  Q ← {v | indeg(v)=0}，按 (-bl(v)) 排序
3  while 未完成:
4      for v in Q (高 bl 优先):
5          if 槽位 capacity(v.resource) 有空:
6              占用槽位；提交 v（若为 LLM，累积到批，攒 batch_interval 后一次提交）
7              Q.remove(v)
8      等待任一 v ∈ R 完成（event/回调）
9      释放 v 的槽位；对其每个后继 u: indeg(u)-=1，若为 0 则入 Q
10     回填: 若某类槽位空闲而 Q 中最长 bl 的前驱未满足，
11           从 Q 中找“后继链最短”的小任务插入（避免空转）
12     失败处理: v 失败 → 后继全部标记 blocked，记录并上报（不静默）
13  return 每任务 (start, finish, wait) + makespan + p90
```

**为什么是这四条的组合**：

| 组件 | 解决什么 | 实验依据 |
|---|---|---|
| 关键路径优先 | 尾部等待（p90） | E1 W3：2.82× vs LPT 2.55× |
| 资源感知准入 | 不让 tool 单槽位成为隐性瓶颈 | §4.6：tool=1 时 4.5s vs 下界 3.8s |
| 批填充 | 减少 LLM 攒批空转 | E3：应用层 vs 原生多 4–16% |
| 回填 | 槽位空转 | 真实负载常有 `schema/docs` 这类 0.3–0.4s 小任务 |

**参数建议**（可写进论文/答辩）：
- `batch_interval`：0.2s（交互）/ 0.5s（吞吐）；
- 每类槽位：llm=1（7B 单卡）~2（双卡/大显存）、tool=4、io=4；
- 优先级函数 `α·bl(v) + β·w(v)`，α=1、β=0.2（小任务略加分，避免饥饿）；
- 失败重试：最多 2 次，指数退避 1s/2s，仍失败则 blocked + 上报。

## §7 原型：`src/scheduler.py`

### 7.1 用法

```python
from src.scheduler import DAGScheduler, Task

tasks = [
    Task("spec",   "planner",  "llm",  [],                              {"estimate_s": 0.9}),
    Task("schema", "writer",   "tool", ["spec"],                        {"estimate_s": 0.4}),
    Task("backend","coder",    "llm",  ["spec"],                        {"estimate_s": 1.2}),
    Task("tool_t", "tester",   "tool", ["backend"],                     {"estimate_s": 0.8}),
    Task("e2e",    "tester",   "tool", ["backend"],                     {"estimate_s": 0.9}),
    Task("review", "reviewer", "llm",  ["backend"],                     {"estimate_s": 0.7}),
    Task("integ",  "reviewer", "llm",  ["tool_t", "e2e", "review"],     {"estimate_s": 0.8}),
]

sched = DAGScheduler(tasks, resources={"llm": 2, "tool": 1, "io": 2}, policy="critical_path")
report = sched.run({"planner": planner_fn, "coder": coder_fn, ...})
print(report.summary())     # makespan / serial / speedup / 失败与阻断
```

### 7.2 已实现的能力

| 能力 | 说明 |
|---|---|
| DAG 校验 | 重复 id、未知依赖、非法资源、环检测（Kahn） |
| 依赖门控 | 前驱全部 `ok` 才放行；上游 `failed` 则下游 `blocked`（不静默） |
| 有界并发 | 按资源槽位准入，不无脑起线程 |
| 优先级 | `critical_path` / `fifo` / `spt` / `lpt` 四种可切 |
| 失败处理 | 任务异常记录并在报告中阻断下游，`ScheduleReport.blocked` 可见 |
| 计时 | 每任务 start/finish/wait（wait = 开始 − 前驱最晚完成） |
| 报告 | `speedup`、`critical_path`、`serial_baseline`、`summary()` |

### 7.3 与赛题代码的接法

1. Planner 产 DAG → 转成 `Task` 列表（`agent` 字段指向四个角色函数）；
2. 角色函数内部调 SDK `llm_chat` 或工具；
3. `DAGScheduler.run()` 的结果写进 JSON 报告，供 [doc/03 §6.2 基准协议](03-赛题对标与多智能体系统设计方案.md) 统计；
4. 若要走真内核：在角色函数里把 `llm_chat` 换成 SDK 的 `llm_chat`（默认打 `/query`），调度器保持应用层。

## §9 风险与反模式

| 风险 | 表现 | 对策 |
|---|---|---|
| **伪加速** | 用"去掉依赖后的理想时间"做基线；预热轮当正式数据；只报最优种子 | 固定 DAG、固定任务集、≥3 轮预热取中位数；报 p90；口径写进文档（doc/03 §6.2） |
| 长任务饥饿 | 一直优先小任务，大 LLM 调用永远排不上 | SPT 只做"尾部优化"，主策略仍 CP/FIFO；设最大等待阈值（如 3× 平均等待） |
| 线程爆炸 | 每个子任务一个线程 + 内核自带线程池 → 争抢 | 应用层有界并发；`agent_factory.max_workers` 调小 |
| 过度分解 | 子任务太多，每次 LLM 调用都带上下文，开销吃掉并行收益 | 按 doc/15 的"粒度下限"（单任务 ≥ 一次有效 LLM 调用）；观测等待占比 |
| 依赖死锁 | 环 / 前驱永远不完成 | 调度前环检测；失败即 blocked 并上报 |
| 攒批放大延迟 | 小请求等 1s 批 | `batch_interval` 调小；演示用 0.2s 并显式说明 |
| 忽视 p90 | 平均好看、用户体验差 | 报告同时给 makespan 与 p90 等待 |
| 策略抖动 | 频繁切策略导致缓存失效（前缀缓存被打散） | 一个 episode 内不切策略；同角色请求连续提交 |
