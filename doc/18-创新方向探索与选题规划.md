# doc/18 创新方向探索与选题规划

> 面向赛题：2026 全国大学生计算机系统能力大赛·操作系统设计赛《智能体操作系统中的多智能体协作技术》
> 输入：`doc/`（11 份调研/设计文档 + 方法规范）与 `vendor/`（12 个上游仓库快照，含可修改的 AIOS 内核与 Cerebrum SDK）
> 目标：把"已经调研清楚的事实"转成"能拿分、能答辩、能按期交付"的创新选题组合。
> 原则：**创新 = 位置 × 策略 × 证据**（`doc/11` §3.4.2）。不声称"世界首个"，只声称"我们把 X 放到了 AIOS 的 Y 位置、用 Z 策略、并给出可复现的 measurements"。

## §1 评判口径：什么样的"创新"在这个赛题里算数

### 1.1 四维打分

| 维度 | 定义 | 权重 |
|---|---|---|
| **创新性** | 是否在"位置/策略/证据"至少一项上超出 `doc/11` 核实的 10 个开源实现 | 30% |
| **可实现性** | 是否能在现有 vendor 代码上改（不重写）、7B 端侧能跑 | 25% |
| **可测量性** | 是否能产出"串行 vs 并行"的墙钟数字 + 消融 | 25% |
| **赛题契合** | 是否直接服务四条要求与 50% 应用效果评分 | 20% |

### 1.2 已核实的"别人做到哪了"（决定我们不能声称什么）

来自 `doc/11` §4–§6（逐仓库查源码，全部带 `路径:行号`）：

- **依赖门控**：camel `Workforce` 有（`vendor/camel/camel/societies/workforce/workforce.py:4491-4493`），LangGraph Pregel 有依赖边触发（`_algo.py:470-486`），agentflow 有 Kahn 分层（`src/scheduler.ts:78-135`）→ **不能声称"首个依赖感知调度"**。
- **但四家都没有**：① 接进 AIOS 的请求生命周期；② 关键路径优先级；③ 7B 端侧串并行实测；④ 与内核批处理协同的调度。→ **这四点是可辩护的空白**。
- AIOS 内核：固定 `batch_interval=1.0s`（`fifo_scheduler.py:70`）、非 LLM 每类单线程、无优先级/无依赖/无全局并发上限 → **"改内核"是真空白**（`doc/09`、`doc/17` §5）。
- 没有开源实现给出 7B 的 serial-vs-parallel 数字（`doc/11` §5.5 核实 10 个仓库）→ **"给数字"本身就是贡献**。

### 1.3 两条硬约束

1. **所有"加速"必须能在同一台机器、同一模型、同一 DAG 上复现**（`doc/03` §6.2 协议）；否则不写进材料。
2. **每个方向至少要有一条"消融"**：关掉该机制后加速比掉到多少——否则无法证明"是它带来的"。

## §3 候选方向详解

### D1 应用层依赖感知调度（TSU + CP-RA）——核心骨架

**问题**：AIOS 的 `syscall` 提交即同步等待（`aios/syscall/syscall.py:185-186`），
内核对依赖一无所知；框架层的 DAG（LLMCompiler/camel）又不在 AIOS 里。于是"能并行的任务被写成了串行代码"。

**机制**：应用层 TSU（Task Scheduling Unit）持有 DAG，按入度门控提交、按关键路径排序、按资源类别限并发；内核只负责它擅长的"批 + 四队列"。

**为什么算创新**（三条，全部可核实）：
1. **位置**：依赖调度第一次出现在 AIOS 的**应用层**（而非框架内部），且与内核批处理协同——`doc/11` 核实的 10 个仓库都没有 AIOS 集成。
2. **策略**：关键路径优先 + 资源感知 + 回填；对照实验证明"容量 > 排序，排序优化 p90"（`doc/17` §4）。
3. **证据**：给出 4 种负载 × 6 种策略 × 30 seeds 的矩阵 + 真实线程演示 + 可复现脚本。

**落地位置**：`src/scheduler.py`（已有）、`src/orchestrator.py`（待写：Planner→DAG→调度器→四角色）、与 `vendor/AIOS` 的 `/query` 对接。

**怎么验证**：

| 实验 | 设计 | 预期 |
|---|---|---|
| E-A 角色并行 | 同 DAG，调度器开/关，各 5 轮取中位数 | ≥1.5×（原型 1.55×） |
| E-B 策略消融 | CP vs FIFO vs SPT | CP 的 p90 等待最低；SPT 在紧配置下变坏（+17%） |
| E-C 资源扫描 | tool 1→2 | +22%（1.55→1.89×） |
| E-D 真机 | 7B + vLLM，4 角色任务看板 | ≥1.25×（赛题红线） |

**风险**：低。唯一要注意的是"别把串行基线写快了"（见 §7 伪加速）。

---

### D2 自适应批窗口（内核级创新）——最硬的一个

**问题**：`fifo_scheduler.py:70` 把 `batch_interval` 写死 **1.0s**。对离线吞吐这是合理攒批，对交互式多智能体是**纯等待**：一个单请求也要等满 1 秒才发车；而演示时 4 个角色交替调用，绝大多数批次只有 1 个请求。

**机制**：把"固定睡 1s"换成**双目标自适应窗口**：

```
每轮 drain 前判断：
  drain_now  ← (队列深度 ≥ K)                       # 有批可攒，等满一批再走
             or (最老请求等待 ≥ W_max)               # 防饿死，≤200ms
             or (本请求在关键路径上 且 DAG slack < S)  # 关键路径要快
  否则 continue 短睡（如 10ms）
K、W_max、S 由应用层调度器通过 hook 传入（DAG slack 只有它知道）
```

**为什么算创新**：AIOS 及 `doc/11` 核实的实现里，批窗口都是**静态配置**；"由 DAG 关键路径余量驱动的批窗口"是把**调度语义注入内核批策略**，这正是操作系统"策略与机制分离"的经典命题（机制=批处理，策略=何时发车）。并且它是**可关可开**的——消融干净。

**怎么验证**：先模拟器估上限（已完成 E5），再做真机 A/B。

E5（`build/sched_batch_sweep.py`，30 seeds，cp，槽位 2/1/2，批开销 0.4s 摊薄）：

| 负载 | interval=1.0s（现状） | 0.2s | 0.05s | 收益（vs 1.0s） |
|---|---|---|---|---|
| W1 看板 6 节点 | 24.51s（1.33×） | 22.91s | 22.64s | **1.070×**（0.05s 时 1.083×） |
| W2 分析 12 节点 | 50.43s（1.35×） | 48.87s | 48.43s | **1.032×**（0.05s 时 1.041×） |
| W3 分层 20 节点 | 44.91s（1.83×） | 42.83s | 42.48s | **1.048×**（0.05s 时 1.057×） |
| W4 重尾 | 67.98s（1.25×） | 66.52s | 66.17s | **1.022×**（0.05s 时 1.027×） |

**读法**：单纯把窗口从 1.0s 压到 0.2s，makespan 再降 2–7%；压到 0.05s 边际收益 <1%。**但压低窗口会牺牲真实 GPU 的批效率**（batch 小 → 吞吐低），所以"自适应"才是正解：有批可攒时等满（K），关键路径紧张时快发。真机 A/B 要同时报 makespan 与 TTFT/p90，并说明吞吐代价。

**落地位置**：`vendor/AIOS/aios/scheduler/fifo_scheduler.py`（`process_llm_requests` + 配置项 `batch_interval` 语义扩展）、`aios/hooks/modules/scheduler.py`（暴露策略参数）、`aios/config/config_manager.py`（新配置 `scheduler.adaptive_window`）。

**为什么它比 D3 更值得做**：①改的是内核，答辩讲"操作系统调度器"名正言顺；②不需要额外显存/多实例；③消融直观（关掉回到 1s）；④工作量 4–6 人日可控。

**风险**：中。真实 vLLM 下"等批"的收益依赖到达率与显存；需要在 7B 单卡上实测校准 K/W_max，并准备"退回静态 0.2s"的降级开关。

### D3 前缀感知 + 角色亲和路由（P1/P2）

**问题**：`adapter.py` 的 `routing_strategy` 只有 `sequential`（轮询）与 `smart`（LP/成本导向）（`vendor/AIOS/aios/llm_core/routing.py`），而**缓存命中率对端侧延迟影响巨大**：SGLang 前缀缓存让共享前缀吞吐 1.67–3.58×（`doc/08` §2）。

**机制**：路由从"轮询"改为"亲和"：
- 同一角色的 system prompt 相同 → 请求**相邻提交**到同一实例（提高 server 端 prefix cache 命中）；
- 多实例时按 **role→instance** 静态亲和（Planner 用 A、Coder 用 B），避免同前缀请求被轮询打散到不同实例。

**怎么验证**：vLLM/SGLang 服务端 `/metrics` 抓 `prefix_cache_hit_rate` 与 TTFT p50/p90；A/B：轮询 vs 亲和，同任务集。预期命中率提升主要在"每轮 system prompt 重复"的场景（看板类任务恰好是）。

**为什么只是 P2**：需要多实例或多模型（显存），且 AIOS adapter 的 batch 是按 model 分组的（`adapter.py:524-531`），改造面比 D2 大；收益也依赖服务端实现细节。

### D4 类型化双向协作协议（P0）

**问题**：自由对话式协作（CAMEL/MetaGPT 类）无法判定"这句话是否算完成"，失败常表现为"看起来在讨论、实际没产出"（MAST 三类失败，`doc/06`：规范/协调/验证）。

**机制**：定义五类消息与状态机（`doc/16` §4 已给出）：

| 消息 | 方向 | 必填字段 | 语义 |
|---|---|---|---|
| `request` | 上游→下游 | task_id, inputs, deadline, acceptance | 派活 |
| `inform` | 任意→任意 | fact, evidence | 广播事实/产物 |
| `critique` | Verifier→Executor | target, issues[], severity | 结构化返工 |
| `commit` | Executor→Verifier | artifact, self_check | 交付待验 |
| `cancel` | 调度器→任意 | reason | 超时/上游失败 |

三条硬规则：① 每条消息带 `task_id` 与 `schema_version`；② `commit` 必须附 `acceptance` 的逐条自检结果；③ `critique` 必须可机读（`issues[]`），否则 Verifier 无效。直接复用 AgentScope `GoalPipeline` 的 executor↔verifier 闭环思想（`_goal_pipeline.py:337-369`：pass/fail/impossible + 反馈回灌）。

**怎么验证**：统计"重做率（critique 次数 / 任务数）"、"无效轮次占比"、"任务成功率"；同样任务集对比"自由对话"基线。**这是协作流程分（60%）的直接抓手，且几乎不占关键路径**。

**风险**：低；工作量主要在 schema 与状态机测试。

### D5 事务化共享工作区（P0，我们的差异化）

**问题**：串行框架（ChatDev/MetaGPT）靠"一次只让一个 agent 写"避免冲突；我们一旦并发，就出现**丢更新 / 半成品被下游读 / 回滚不一致**。这是"并发带来的新问题"，也恰好是操作系统最经典的题目（隔离、事务、一致性）。

**机制**：应用层"工作区事务"：
1. 每个子任务声明 **write set**（`vendor` 已有：Cerebrum `StorageQuery` 的 `write/create_file/rollback/mount`，`cerebrum/storage/apis.py`）；LSFS 底层已有 **文件锁 + 版本历史（max_versions=20）+ restore**（`vendor/AIOS/aios/storage/filesystem/lsfs.py:66-160`，依赖 Redis）。
2. 调度器在任务开始时为其创建**分支视图**（copy-on-write 或 git worktree），完成时按依赖顺序**原子合并**；
3. 合并冲突 → 生成一个 `critique` 任务给 Verifier（复用 D4 协议），失败则回滚到上一版本；
4. 下游只读"已 commit 的版本"，杜绝读半成品。

**为什么算创新**：① 把数据库的"事务/隔离级别"搬进多智能体工作区，且**与 DAG 调度器耦合**（合并时机=依赖完成时刻）；② 有明确的量化指标（丢更新次数、合并冲突率、回滚成功率）；③ 恰好回应"并发会不会把工程搞坏"这个评委必问。

**怎么验证**：写一个"两个 Coder 同时改同一文件 + 一个 Tester 读"的对抗场景：
- 无保护：丢更新率 ~50%（后写覆盖）、Tester 读到半成品；
- 有事务：丢更新 0、读到中间态 0、冲突被显式上报给 Verifier。
再叠加端到端任务成功率与耗时（事务有成本，要证明它没把加速吃掉 >5%）。

**风险**：中（文件锁/Redis 依赖；WSAL 与 git worktree 的选型）。**降级路径**：先做"每任务独立目录 + 依赖完成时合并"，不做细粒度锁。

### D6 失败护栏与动态重规划（P1）

**问题**：7B 端侧失败率高（AgentBench：6B 模型 OA=0.11 vs GPT-4 4.01，`doc/08` §1）；一次失败会让整条 DAG 空转。

**机制**：三道护栏——① **断路器**：同一子任务连续失败 2 次即跳过并由 Verifier 降级产出（或标记 blocked，不静默）；② **动态重规划**：拿到失败证据后只改写下游（TDAG 把级联失败从 32.61% 压到 4.35%，`doc/07`）；③ **早停**：DyLAN 式提前终止省 11.3–66.2% API 调用（`doc/06`）。

**怎么验证**：注入故障（让某个 agent 按概率失败），对比"无护栏 vs 有护栏"的任务成功率与总耗时。预期成功率明显上升，耗时略降（少空转）。

**落地**：作为 `src/scheduler.py` 的钩子（失败回调 + DAG 局部重写），工作量 3–5 人日。

---

### D7 端侧能力路由/降级（P2，合规风险）

按难度把子任务分给 7B 或更强模型（云端/本地更大模型）。收益是质量，风险是**可能被认为"没在端侧跑"**——赛题环境写明端侧 7B/8B。建议只在"允许混合"时作为 demo 的降级兜底，不作为卖点。

### D8 MAS-SpeedBench 基准协议（P1，证据工程）

把 `doc/03` §6.2 的协议 + `doc/17` 的实验固化成 harness：

```text
bench/
  workloads/{board6,analysis12,layered20,hetero}.json   # DAG 定义 + 每任务耗时/资源
  run.py --policy cp --serial/--parallel --repeat 5      # 自动跑、自动出表
```

**为什么是创新（评测层面）**：`doc/11` 核实的 10 个开源实现**都没有 serial-vs-parallel 实测**；一个可复现的对照协议 + 公开脚本，在竞赛/论文语境里是实打实的贡献，也是答辩时"数字可信"的底座。

**成本**：3–4 人日（大部分逻辑 `doc/17` 已有）。

## §6 答辩叙事与必答问题

### 6.1 三条主线

1. **"操作系统视角"**：我们关心的不是"让 LLM 聊起来"，而是**并发、隔离、调度、一致性**四件事——这正是 OS 赛道的评判点。
2. **"每一条都测了"**：串行/并行对照、策略消融、资源扫描、批窗口扫描、冲突对抗；全部可复现（`bench/`）。
3. **"有边界的创新"**：我们承认依赖门控不是首创（camel/LangGraph），创新在"位置 + 策略 + 证据"；承认批窗口不是新概念，创新在"用 DAG slack 驱动内核策略"。

### 6.2 评委八问（预答，摘自 `doc/03` §1.3，此处按新选题更新）

| 问题 | 一句话答案 |
|---|---|
| 为什么单智能体做不了？ | 四类能力（规划/编码/测试/审查）需要不同上下文与工具，单模型 7B 无法同时胜任（AgentBench 6B OA=0.11） |
| 并行从哪来？ | DAG 里 ≥4 个无依赖节点：schema、backend、frontend、docs 同时起（`doc/15` 示例） |
| 加速怎么算的？ | 同 DAG 串行基线 vs 并行墙钟，≥3 轮预热取中位数，报 p90（`doc/03` §6.2） |
| 是不是把串行基线写慢了？ | 基线用同一批 agent 函数、同一模型、同一任务，只把调度器换成"拓扑序串行"；伪加速检查表见 §7 |
| 依赖怎么保证？ | 入度门控 + 前驱完成才提交 + 失败向下游传播 blocked（`src/scheduler.py`） |
| 并发写冲突怎么办？ | D5 事务化工作区：分支写 + 原子合并 + 冲突交 Verifier |
| 7B 端侧凭什么快？ | 端侧瓶颈是批效率与等待；D2 把"固定等 1s"变成"按需发车"，D1 把工具等待与推理重叠 |
| 与开源项目的区别？ | 位置（AIOS 应用层 + 内核批策略）、策略（关键路径 + slack 驱动批窗口）、证据（7B 实测 + 消融） |

## §7 不做清单（避免踩坑）

| 不做 | 原因 |
|---|---|
| 辩论/自组织/自由群聊 | 7B 上通信成本高、失败放大（`doc/16` §3）；且难以给加速数字 |
| 多机分布式 | 赛题环境单机端侧；增加部署风险，收益无法在评委机器复现 |
| 自研推理引擎 | 与 OS 赛道无关，且 vLLM/SGLang 已足够（`doc/08`） |
| 云端为主 | 赛题写明端侧 7B/8B；D7 只作兜底 |
| 追求"首个"表述 | `doc/11` 已核实同类实现；过度宣称会在答辩被拆穿（`doc/03` §3.4.2） |
| 把 1s 攒批直接改成 0（不做自适应） | 牺牲真实吞吐；要的是"按需等待"而非"完全不等待" |

**伪加速自检表**（答辩前逐条打勾）：

- [ ] 串行/并行用同一模型、同一 prompt、同一任务集、同一机器
- [ ] ≥3 轮预热，取中位数，报 p90，不只报最好一轮
- [ ] 并发带来的写冲突已被 D5 处理（否则"快"是错误换来的）
- [ ] 关掉 D1/D2 后能复现串行基线（消融可逆）
- [ ] 网络/磁盘缓存副作用已排除（重启服务、固定顺序）
