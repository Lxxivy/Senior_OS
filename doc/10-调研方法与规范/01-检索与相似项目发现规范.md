## 1. 第一步不是搜，而是定义"什么算相关/相似"

### 1.1 六维相似性

只用一个"相似度"数字，必然退化成"关键词像不像"。正确做法是把"相似"拆成六个可独立判断的维度，分别打分、分别给证据。

| 维度 | 要回答什么 | 判断强度 | 本项目可观察锚点 | 合格证据 |
| --- | --- | --- | --- | --- |
| 问题定义 | 它解决的问题是否与本项目同一件事？ | **必须** | 在资源受限（端侧 7B）下，多智能体并行完成可分解、有依赖的复杂任务 | 摘要/引言的问题陈述、系统输入输出定义 |
| 核心机制 | 关键机制是否相同或可替代？ | **必须** | 任务 DAG 表达依赖、就绪队列调度、并行执行器、子任务结果合并 | 方法章节小节＋代码函数/行号 |
| 系统架构 | 组件划分与数据流是否同构？ | 建议（强证据） | 内核层（调度/上下文/工具）＋编排层（DAG/角色/消息总线）分层 | 架构图、目录树、模块表 |
| 实验场景与数据 | 验证场景与数据是否可对比？ | 建议 | 单机/端侧、并发任务、真实软件任务、相对串行的加速比 | 实验章节表号、数据集名、硬件配置 |
| 代码实现 | 机制是"说了"还是"写了"？ | 不单独作为相似依据，但决定证据等级 | 调度循环、依赖解析、批处理逻辑可定位到函数 | 仓库 `文件:行`、测试、License |
| 技术栈 | 运行平台/语言/框架是否兼容？ | 不单独作为依据（只作筛选标签） | Python 3.10/3.11、Linux、FastAPI、vLLM/SGLang | requirements / pyproject |

**判断强度的含义**：标"必须"的维度为 0 分时，该候选**不能**被称为"相似项目"，最多算"可借鉴的相关工作"；标"建议"的维度只用于提升或降低结论等级；标"不单独"的维度只记录、不参与加权（代码实现改作乘子，见 §6.2）。

### 1.2 权重：设计参数，不是最优值

GPT 讨论给出的"核心功能 40%／系统架构 30%／算法与实现 20%／应用场景 10%"是**示例配置**，原文明确写着"这些是可调整的设计参数，并非经过实验验证的最优值"。本规范沿用其数量级，但按本项目关注点重映射维度：

| GPT 讨论原维度 | 原权重 | 本规范维度 | 权重 | 改造理由 |
| --- | --- | --- | --- | --- |
| 核心功能 | 40% | 问题定义 | 40% | 同义，改为可检验的表述 |
| 系统架构 | 30% | 系统架构 | 20% | 论文常夸大"架构不同"，且架构差异往往可由机制差异推出，降权 |
| 算法与实现 | 20% | 核心机制 | 30% | 本项目最关心"并行与依赖调度"机制，升权 |
| 应用场景 | 10% | 实验场景与数据 | 10% | 保留，但要求"同约束"才给 3 分 |
| （未列） | — | 代码实现 | 不计权，作证据系数 k | 防止"宣称支持"拿高分 |
| （未列） | — | 技术栈 | 不计权，作筛选标签 | 只用于排除不可运行平台 |

**使用声明（强制）**：任何使用本权重产出的评分表，必须在表头下一行写明——"权重为经验设定（40/30/20/10，代码系数 0.85–1.00），未做权重敏感性实验"。不写这句，评分表视为过程材料，不得进入交付文档。

**两条否决规则**：

1. 问题定义 = 0 → **直接淘汰**。问题不同，机制再像也只是"相关文献"，不能进相似项目对比表。
2. 问题定义 ≥2 且（核心机制 + 系统架构）= 0 → 降为"观察"。说明主题相关但无可借用的实现。

### 1.3 相关 ≠ 相似 ≠ 同源

三者混用是检索报告最常见的失真来源。先判关系类型，再决定投入多少成本：

| 关系 | 定义 | 本项目例子 | 用途 | 处理 |
| --- | --- | --- | --- | --- |
| 相关（related） | 主题同域、可互相引用，但机制不可替代 | 多智能体综述 vs 本项目 DAG 调度器 | 相关工作章节、背景论证 | 进候选池，评分最多到"相关"档 |
| 相似（similar） | 问题同，机制或架构可替代 | LLMCompiler 的 DAG 并行执行 vs 本项目调度器 | 方案借鉴、对比实验 | 进精读队列，要求 ≥2.5 分 |
| 同源（derived） | Fork／镜像／同一作者系列／版本变体 | AIOS 论文与 AIOS 仓库；`vendor/AIOS` 与上游 | 去重、引用版本选择 | 合并为一条，标注 upstream |

## 2. 检索路径矩阵

### 2.0 五条路径总览

单条路径必有盲区，必须多路并行。下表是入口与产出；具体命令见 §2.1–§2.5。

| 路径 | 能解决什么 | 主要产出字段 |
| --- | --- | --- |
| a 关键词检索 | 快速铺开领域地图，建立初期候选 | 标题、年份、venue、摘要、链接 |
| b 引用链 | 找到关键词漏掉的奠基工作与后续改进 | 前向/后向关系、被引数、被谁引用 |
| c 代码搜索 | 找"README 没写但代码实现了"的项目 | 仓库、`文件:行`、命中关键词 |
| d 现成相似项目工具 | 冷启动候选清单，快速判断"有没有同类" | 相似仓库列表、工具给出的理由 |
| e 领域术语扩散 | 补第一轮因术语不同而漏掉的 | 新术语 → 新检索式 → 新增候选 |

### 2.1 路径 a：arXiv API / Semantic Scholar 关键词检索

**入口与可复制片段**（本机 pwsh 直连 HTTPS 失败、Python 可用，见 [00](../00-调研总览与索引.md) §8，故统一用 Python）。第一段演示 arXiv 检索：每轮固定 `max_results=50` 与 `sortBy=relevance`，否则不同轮次的召回率不可比。

```python
import urllib.parse, urllib.request
q = 'all:"multi-agent" AND all:"task decomposition"'
url = "http://export.arxiv.org/api/query?" + urllib.parse.urlencode({
    "search_query": q, "start": 0, "max_results": 50,
    "sortBy": "relevance", "sortOrder": "descending"})
raw = urllib.request.urlopen(url, timeout=30).read().decode("utf-8")
```

**Semantic Scholar** 走 Graph API 的 `paper/search` 端点，只取标题、年份、会议、被引数、外部 ID 与摘要等元数据字段：

```python
url = ("https://api.semanticscholar.org/graph/v1/paper/search?"
       "query=multi-agent%20task%20scheduling&limit=50"
       "&fields=title,year,venue,citationCount,externalIds,abstract")
```

**查询词构造规则**：

1. 一个概念组一条检索式，不要把所有概念塞进一条（见 §3.2 R1）。
2. arXiv 字段前缀：`ti:`（标题）、`abs:`（摘要）、`all:`（全字段）；短语必须加引号。
3. 布尔用 `AND`/`OR`/`ANDNOT` 显式连接，不依赖隐式空格。
4. 每轮固定 `max_results` 与排序方式（`relevance`），并写进日志。
5. 请求串行、间隔 ≥3 秒（与 [`build/fetch_papers.py`](../../build/fetch_papers.py) 的下载节奏一致），避免被封。

**已知限制**：arXiv API 只匹配元数据（标题/摘要），摘要里没写机制词的论文会漏；Semantic Scholar 无 key 时共享配额、易限流，字段与配额以官方文档为准（**待验证**）。**产出字段**：标题、arXiv ID、年份、摘要、作者、链接。

### 2.2 路径 b：引用链（后向参考文献 / 前向被引）

**后向**（从命中论文往回找奠基工作）：Semantic Scholar `GET /graph/v1/paper/{paperId}/references?fields=title,year,venue,externalIds&limit=100`；也可直接读抽取文本的 References 段（`build/papertext/` 已由 `pdftotext -layout` 生成，用 `grep` 定位 `References`）。

**前向**（看谁引用了它）：`GET /graph/v1/paper/{paperId}/citations?...`；Google Scholar 则在论文页下方"被引用次数"逐条点开（无官方 API，人工操作）。

**规则**：

1. 只对"核心 5 篇"做完整前后向，否则组合爆炸。
2. 前向只展开"标题含目标机制词"的引用（如 DAG、parallel、scheduling），其余只记数量。
3. 被引数只反映影响力，**不反映相似度**，不得作为评分维度。

**已知限制**：前向引用受收录范围影响，新论文、工程文章、非英文工作常缺失；被引数为 0 不代表不重要。**产出字段**：关系方向、对方标题/ID/年份、被引数、是否含目标机制词。

### 2.3 路径 c：GitHub Code Search 与 README 搜索

**目的**：找"README 没写、但代码里确实实现了"的项目。这是纯关键词检索与工具推荐都覆盖不到的一层。

```powershell
gh auth login
gh search repos "multi-agent orchestration" --match readme --limit 100
gh search repos "task DAG scheduler" --match readme --limit 100
gh search repos "agent workflow engine" --match readme --limit 100
```

仓库搜索覆盖 README 与仓库元数据；代码搜索要**用特征性函数名/算法名，而不是项目名**，用来发现"实现里有、README 没写"的项目：

```powershell
gh search code "topological_sort" --language python --limit 100
gh search code "depends_on" --language python --limit 100
```

**规则**：

1. 上面三条仓库搜索是**三个独立检索**，不是要求一个仓库同时满足三个条件（GPT 讨论原话："这里是三个独立搜索，而不是要求每个仓库同时满足三个条件"）。
2. 用 `--match readme` 限定匹配范围，避免项目名噪声。
3. 单一查询上限 1,000 条（GitHub REST 搜索限制，**二手，未实测**），大结果集必须拆查询。
4. Code Search **不支持穷尽式搜索**（**二手，未实测**），只能作补充召回，不能用来证明"没有同类项目"。

**产出字段**：仓库全名、stars、License、命中文件与行、命中关键词、README 是否提及该机制。

### 2.4 路径 d：现成相似项目工具

| 工具 | 能力 | 已知限制 | 本项目状态 |
| --- | --- | --- | --- |
| GitHub Repo Radar | 输入仓库链接 → LLM 提取特征 → 多路搜索与语义排序 | 主要分析仓库信息与 README，**不逐行理解代码** | 未实测 |
| Related Repos | 直接搜仓库并发现相关开源项目，适合快速形成初筛清单 | 不能据此保证找全 | 未实测 |
| Replore | 输入参考仓库＋补充搜索要求，混合检索；也支持从需求描述出发 | 依赖其索引覆盖 | 未实测 |
| MetaSim（ICSME 2024） | 学术工作：以 GitHub 仓库为查询样本找功能相似仓库，数据集约 **26.76 万**公开仓库，人工评估报告了较高的相似性精确率 | 报告的是"精确率"不是"找全率"，且不等效于本项目语言栈与场景 | 二手，未实测 |

> 以上四项均出自 `doc/GPT关于调研的讨论.md`，本仓库**没有安装或实测**。引用时统一加"（二手，未实测）"；写进交付文档时必须标为"候选工具"，不得写成"已验证可用"。

**定位**：路径 d 只用于**冷启动**（30 分钟内形成 10–20 条候选），随后必须回到 a/b/c/e 做可追溯的验证。

### 2.5 路径 e：领域术语扩散

从三类来源抽新词，回到 §3 建新检索式：

| 来源 | 抽什么 | 本项目示例 |
| --- | --- | --- |
| 命中论文的方法章节 | 机制术语、算法名 | LLMCompiler → "parallel function calling"、"task DAG" |
| 综述的分类体系 | 类别名、对照维度 | 多智能体协作综述的五维分类（见 [02](../02-多智能体协作机制综述-中文翻译与总结.md)） |
| 评审意见 / 竞品文档 | 同义改写、行业叫法 | "workflow engine" vs "agent orchestration" |

**规则**：每个新词先判断"新概念还是同义改写"——同义改写并入同义词表（§3.1），新概念单开一组并写一条新检索式；每个新词都要留下"从哪篇哪节抽的"。

## 3. 检索式构建规范

### 3.1 中英同义词表模板（含 4 组真实示例）

| 组号 | 中文概念 | 英文主词 | 同义/变体 | 缩写 | 排除词 |
| --- | --- | --- | --- | --- | --- |
| 1 | 智能体操作系统 | LLM agent operating system | agent OS, AIOS kernel, LLM as OS, agent runtime | AIOS | OS kernel（传统内核论文） |
| 2 | 多智能体协作 | multi-agent collaboration | multi-agent system, LLM agent collaboration, agent society | MAS | MARL（多智能体强化学习，除非做调度） |
| 3 | 任务调度 | task scheduling | agent scheduling, request scheduling, concurrency control, batching | — | CPU scheduling（传统 OS） |
| 4 | 依赖 DAG | task DAG | dependency graph, task graph, DAG scheduling, topological order | DAG | blockchain DAG |

**模板字段说明**：中文概念（内部统一叫法）｜英文主词（arXiv/S2 首选词）｜同义/变体（扩召回用）｜缩写（常出现在标题里）｜排除词（防领域串台，必须写）。每组变体建议 3–8 个，少于 3 个说明还没想清，多于 8 个应先合并同义项。

### 3.2 布尔与短语规则（六条）

| 编号 | 规则 | 反例 → 正例 |
| --- | --- | --- |
| R1 | 一次只检索一个概念组，多概念用多轮而非一条 AND | `multi-agent task dag scheduling parallel` → 分 3 条独立检索 |
| R2 | 短语加引号，避免单词碎片 | `task dag` → `"task dag"` |
| R3 | 组内同义词用 OR 扩召回，跨组才用 AND 收窄；AND 超过 2 个先试跑，命中 <5 视为过窄 | `"agent" AND "dag" AND "parallel" AND "7b"` → 先两两组合 |
| R4 | 适配平台语法：arXiv 用 `ti:/abs:/all:`；S2 不吃布尔，改自然语言并多次改写；GitHub 用 `--match readme`、`language:`、`stars:>50` | 把 arXiv 的 `ANDNOT` 直接贴到 S2 → 无结果 |
| R5 | 每轮只改一个变量（只换同义词或只换平台），否则无法归因 | 同时换平台+换词 → 命中变化说不清原因 |
| R6 | 排除词必须写进查询，否则传统 OS、MARL 类结果会淹没候选池 | 不写 `-MARL` → 前 50 条一半是强化学习 |

### 3.3 每轮记录"查询 → 命中数 → 新增入池数"

| 轮次 | 查询式 | 平台 | 命中数 | 新增入池 | 备注（示例） |
| --- | --- | --- | --- | --- | --- |
| 第 1 轮 | `all:"multi-agent" AND all:"task decomposition"` | arXiv API | 187 | 9 | 多为对话式编排，DAG 类少 |
| 第 1 轮 | `task DAG scheduler --match readme` | GitHub CLI | 63 | 4 | 多为 workflow 引擎 |
| 第 2 轮 | `"parallel function calling"` | arXiv API | 21 | 3 | 术语扩散所得 |

> 上表数值为**格式示例**，不是本项目实测值；真实数字以检索日志（§8）为准。这张表的作用是让"哪条检索式有效"可比较：新增入池/命中数的比值高，说明该检索式精准。

## 4. 候选池与去重

### 4.1 候选池表结构

| 编号 | 标题 | 来源路径 | 年份 | 链接（arXiv/仓库） | 六维分（问题-机制-架构-场景-代码-栈） | 加权分 S | 状态 | 入池理由 | 证据位置 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| C-001 | AIOS: LLM Agent Operating System | a 关键词 | 2024 | 2403.16971 | 3-3-3-2-3-3 | 2.90 | 进池 | 赛题点名基线，内核调度与 syscall 可直接对照 | 方法 §3；`vendor/AIOS/aios/scheduler/` |
| C-002 | An LLM Compiler for Parallel Function Calling | b 引用链 | 2023 | 2312.04511 | 2-2-2-1-2-2 | 1.81 | 进池 | DAG 并行执行机制参考，"≥20% 加速"的主要依据 | 论文方法章节（代码级核对未做，按 §6.3 记为未核实） |

**字段规则**：编号唯一且不复用（淘汰的编号作废）；来源路径填 a–e 字母；六维分写 6 个数字，顺序固定；状态只有"进池/观察/淘汰"三态；入池理由一句话说明"要从中拿什么"；证据位置必须能定位（章节号或 `文件:行`）。

### 4.2 去重规则

| 情形 | 判定依据 | 处理 |
| --- | --- | --- |
| 同 DOI / 同 arXiv ID | 标识符相同 | 合并为一条，保留正式版元数据，记录所有版本 |
| arXiv v1/v2/v3 | 同一 ID 不同版本 | 同一条目；引用最新版并写版本号，数字以最新版为准 |
| 预印本 vs 会议版 | 标题＋作者高度重合 | 合并；数字冲突时以正式版为准并注明差异 |
| Fork / 镜像 / 子目录 | 见 §4.3 | 关联 upstream；无实质增量则合并 |
| 同一作者系列论文 | 作者与主题延续（如先规划后分解的系列） | **不合并**，标注"同源系列"，避免重复引用与重复计数 |
| 同名不同工作 | 作者/年份/摘要不同 | 分开；唯一键用 ID，不用标题 |

### 4.3 Fork / 镜像判定

五项检查，命中 ≥3 项即判为 Fork：

1. 仓库页是否有 "forked from" 标记；
2. `git log` 是否保留上游 commit 与作者（溯源可见）；
3. README 是否声明 upstream / mirror / 中文翻译版；
4. 目录结构与上游高度重合，而新增文件占比很低；
5. 是否有独立的版本号、论文或 benchmark。

**处理阈值**：判为 Fork 的，记录 upstream URL 与差异文件数；只有当"新增代码或新增 benchmark 占比 ≥30%"（经验阈值）时才允许作为独立候选，并在池中注明"源自 X，增量 Y"。**本项目注意**：`vendor/AIOS`、`vendor/owl` 是以 `git subtree` 引入的**项目快照**（见 [09](../09-AIOS与OWL代码库调研与SDK实践.md) §2.4），不是两个独立相似项目，评分只算一条。

### 5.1 两轮流程

### 5.2 术语抽取表

## 6. 相似度评分卡

### 6.1 四档锚点

评分必须按"可观察锚点"打，不许凭感觉。下表每格都是"能看到什么就给几分"：

| 维度 | 0 分 | 1 分 | 2 分 | 3 分 | 证据落在哪 |
| --- | --- | --- | --- | --- | --- |
| 问题定义 | 不同问题（如单 agent 提示工程） | 同领域但目标不同（都是 LLM 应用，但做 RAG） | 同问题家族、约束不同（多 agent，但对话式而非任务调度） | 同问题同约束（多 agent 并行执行可分解任务、资源受限） | 摘要/引言的问题陈述、系统输入输出 |
| 核心机制 | 未涉及目标机制 | 仅概念提及（related work 里出现 "DAG"） | 有机制描述与算法伪代码，无实现细节 | 代码级实现同一机制，可指到函数/类 | 方法章节＋仓库 `文件:行` |
| 系统架构 | 单体脚本，无分层 | 有分层但组件不对应 | 相似的组件划分（planner/executor/memory） | 组件边界与数据流可与本项目一一映射 | 架构图、目录树、模块表 |
| 实验场景与数据 | 无实验或玩具示例 | 单一 benchmark、场景不同 | 场景相近（任务自动化/软件工程），指标不同 | 同场景同约束（端侧、并发、真实任务），数字可直接对比 | 实验章节表号、数据集、硬件 |
| 代码实现 | 无公开代码 | 有仓库但只是 demo/文档 | 核心机制有可运行实现，但依赖重、难剥离 | 可直接复用/移植，有测试与清晰 License | 仓库 URL、`文件:行`、LICENSE |
| 技术栈 | 平台冲突（不可用） | 部分兼容（需重写） | 兼容（Python/Linux） | 同栈同版本约束（Python 3.10/3.11、FastAPI、vLLM） | requirements / pyproject |

### 6.2 加权公式与计算

$$S = (0.40 \cdot s_{问题} + 0.30 \cdot s_{机制} + 0.20 \cdot s_{架构} + 0.10 \cdot s_{场景}) \times k_{代码}$$

其中 $k_{代码}$ 按"代码实现"维度取值：3 → 1.00，2 → 0.95，1 → 0.90，0 → 0.85。技术栈不计分，只用于排除不可运行平台。

| 候选 | 问题 | 机制 | 架构 | 场景 | k 代码 | S | 结论 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| AIOS（C-001） | 3 | 3 | 3 | 2 | 1.00 | 2.90 | 核心相似 → 精读 |
| LLMCompiler（C-002） | 2 | 2 | 2 | 1 | 0.95 | 1.81 | 相关 → 相关工作引用 |
| 某对话式编排框架 | 2 | 1 | 1 | 1 | 0.95 | 1.33 | 观察 → 留池不再投入 |

**强制声明**：权重、k 系数、下方阈值全部是经验设定，**未经实验验证**；换任务（如改做 GUI 自动化）需要重新校准，不得直接套用。

### 6.3 证据列：区分"宣称支持"与"我方核实"

每一条评分必须同时写两列，缺一列即视为未完成评分：

| 候选 | 维度 | 分 | 来源宣称 | 我方核实 | 证据位置 |
| --- | --- | --- | --- | --- | --- |
| AIOS | 核心机制 | 3 | 论文称 kernel 负责任务调度与 LLM syscall 批处理 | 已读源码确认调度线程与批处理逻辑 | [09](../09-AIOS与OWL代码库调研与SDK实践.md) §3.1；`fifo_scheduler.py:33`、`rr_scheduler.py:32` |
| AIOS | 实验场景 | 2 | 论文报告最高 2.1× 吞吐提升；调度总耗时 152.1 / 74.2 / 77.3 秒（无 AIOS / FIFO / RR） | 已回原文与 [01](../01-AIOS-中文翻译与总结.md) §5 核对，数字一致 | [00](../00-调研总览与索引.md) §6 第 1 条 |

**规则**：① "我方核实"只能是三种值——"已读代码确认"/"已复现"/"未核实"；② 未核实的最高只能给 2 分（代码实现维度除外，该维按有无实现直接判）；③ 证据位置写到章节号或 `文件:行`，不接受"官网说明""README 提到"。

### 6.4 结论阈值

| 加权分 S | 结论 | 动作 |
| --- | --- | --- |
| ≥2.5 | 核心相似 | 进精读队列；在交付文档中单列"相似项目对照" |
| 1.8–2.5 | 相关 | 进"相关工作"章节，不单独精读 |
| 1.0–1.8 | 观察 | 留池，不投入精读成本 |
| <1.0 | 淘汰 | 写一句淘汰理由，归档 |

阈值是经验值，需随 gold set 的实测结果校准（例如发现漏判严重时下调 2.5 的门槛）。

## 7. 检索质量评估

### 7.1 构造 gold set（10 篇已知必读）

从 [00](../00-调研总览与索引.md) §2 的 25 篇里挑出 10 篇作为"基准答案"。选的标准：赛题点名 2 篇 + 五个环节各 1–2 篇机制关键文献。

| 编号 | 论文 | arXiv | 为什么必读 |
| --- | --- | --- | --- |
| G1 | AIOS: LLM Agent Operating System | 2403.16971 | 赛题点名基线 |
| G2 | Multi-Agent Collaboration Mechanisms: A Survey | 2501.06322 | 赛题点名综述 |
| G3 | MemGPT | 2310.08560 | 上下文/内存管理 |
| G4 | Autellix | 2502.13965 | agent 感知的服务调度 |
| G5 | AutoGen | 2308.08155 | 对话编排事实标准 |
| G6 | MetaGPT | 2308.00352 | SOP 流水线 |
| G7 | Why Do Multi-Agent LLM Systems Fail?（MAST） | 2503.13657 | 失败分类与实证 |
| G8 | An LLM Compiler for Parallel Function Calling | 2312.04511 | DAG 并行执行 |
| G9 | AgentBench | 2308.03688 | agent 评测口径 |
| G10 | vLLM / PagedAttention | 2309.06180 | 服务层并发 |

**注意**：gold set 会过时（新论文天然不在其中），每季度或每接手新批次后扩充；gold set 只用于**校准检索路径**，不是"必读清单"本身。

### 7.2 Recall@K 与 Precision@K

$$\text{Recall@}K = \frac{|\text{Top-}K \cap \text{Gold}|}{|\text{Gold}|}, \qquad \text{Precision@}K = \frac{|\text{Top-}K \cap \text{Gold}|}{K}$$

**算例**（示例数值，用于说明口径）：gold = 10 篇；某轮 arXiv 检索返回 50 条，按相关度取前 20 命中 7 篇，其中前 10 命中 5 篇 → Recall@20 = 7/10 = **0.70**，Precision@10 = 5/10 = **0.50**。第二轮用术语扩散补检后 Recall@20 = **0.90**（新增 2 篇）。

**读法**：Recall 低说明"漏"，要加路径或换术语；Precision 低说明"噪声大"，要收窄检索式。**不承诺"找全"**：Recall 只衡量"相对 gold 的覆盖"，gold 本身可能不全（见 §7.4）。

### 7.3 每条路径的独有命中

| 路径 | gold 命中 | 独有命中 | 结论 | 下轮动作 |
| --- | --- | --- | --- | --- |
| a arXiv 关键词 | 7 | 3 | 覆盖面广、噪声多 | 保留，优化检索式 |
| b 引用链 | 6 | 2 | 精准但滞后 | 核心 5 篇必查 |
| c GitHub README/Code | 2 | 1 | 补工程实现有效 | 第二轮加跑 |
| e 术语扩散 | 3 | 2 | 补漏最有效 | 固定为第二轮必做 |

**规则**：独有命中 = 其他路径都没找到的 gold。某路径独有命中连续两轮为 0 → 下轮降级或淘汰，把时间还给有效路径。上表数值为示例，真实值以日志与 gold 比对结果为准。

### 7.4 平台限制与"不承诺找全"

| 平台/路径 | 已知限制 | 后果 | 报告写法 |
| --- | --- | --- | --- |
| GitHub REST 搜索 | 单次查询最多返回 1,000 条（二手，未实测） | 大结果集无法穷尽 | "GitHub 搜索上限 1000，已按 N 个查询覆盖" |
| GitHub Code Search | 不支持穷尽式搜索（二手，未实测） | 只能补充召回 | "代码搜索为非穷尽" |
| arXiv API | 只匹配元数据（标题/摘要），无全量检索能力 | 摘要未写机制词的工作会漏 | "关键词仅覆盖元数据" |
| Semantic Scholar | 覆盖不全、配额有限、被引数滞后 | 前向引用链不完整 | "引用链受收录范围限制" |
| Google Scholar | 无官方 API、有反爬 | 无法程序化全量 | "人工抽查 N 篇" |

**报告用语规范**：禁止写"已全面调研""已找全所有相关工作"；应写"截至 2026-11-18，覆盖 a/b/c/e 四条路径（d 工具未实测），已知遗漏：非英文文献、未公开仓库、检索日之后的新论文"。

```csv
date,searcher,path,query,platform,hits,new_candidates,dedup_dropped,note
```

### 8.2 填写示例

```csv
2026-11-17,spec-a,a,all:"multi-agent" AND all:"task decomposition",arXiv API,187,9,2,命中多为对话式编排，DAG 类少
2026-11-17,spec-b,c,"task DAG scheduler" --match readme,GitHub CLI,63,4,1,workflow 引擎居多，需 code search 补充
```

### 8.3 归档规则

3. 日志是"我们真的找过"的唯一证据，**不得事后补写**；补写的行必须标 `note=补记`。
