## 0. 一句话复盘

**用「1 名主控 + 6 名并行子代理 + 任务板互斥写入 + 七节论文卡片 + 数字回源抽查」，在约 4 小时内把 25 篇论文与 2 个代码库整理成 11 份、共 11.2 万字的中文文档；最大的收获不是文献本身，而是暴露了三个流程缺口——检索召回没有量化、二手信息没有先核验、初稿数字没有强制标表号——本规范正是为补这三个洞而写。**

## 3. 检索与选文复盘

### 3.1 实际用了哪些检索路径

| 路径 | 实际用法 | 效果评价 |
| --- | --- | --- |
| 赛题锚点 | 直接采用赛题点名的 AIOS（2403.16971）与协作综述（2501.06322） | ★★★★★ 省掉“从哪开始”的纠结，天然形成 gold set |
| 综述章节扩散 | 从 2501.06322 的分类章节抽“协作机制 / 拓扑 / 协调协议”等术语再检索 | ★★★★☆ 一次换来 5 篇协作框架 |
| 引用链后向 | 从 AIOS 与 LLMCompiler 的参考文献追 MemGPT、ReWOO 等 | ★★★★☆ 找到了“机制源头”，避免只读最新综述 |
| 关键词检索 | arXiv API 按 `multi-agent`、`task decomposition`、`parallel function calling`、`agent serving` 等 | ★★★☆☆ 有效但噪声大，需人工筛 |
| 代码检索 | 用 GitHub 源码定位 AIOS 的调度器、SDK、上下文管理 | ★★★★☆ 揭穿了论文没写的实现细节（见 §5） |
| **缺失路径** | 没有做前向被引、没有系统跑 Recall@K、没有用相似项目工具 | ☆☆☆☆☆ 这是本规范 [01](01-检索与相似项目发现规范.md) 要补的空白 |

### 3.2 选文的“三看”标准（可复用）

1. **看它回答哪个子问题**：每篇必须能挂到“内核 / 协作 / 失败 / 并行 / 评测”之一的某个具体问题上，挂不上的不读。
2. **看它有没有可回源的数字**：实验论文要能给出加速比、成功率、成本；纯愿景论文（如 2312.03815）只读机制，不期待数字。
3. **看它和我们方案的差异**：读完要能回答“我们和它不一样在哪”，否则说明这篇只是背景资料，放进 `doc/articles/` 即可。

## 4. 分工与并行复盘

### 4.1 有效做法

| 做法 | 具体实现 | 收益 |
| --- | --- | --- |
| 任务板先行 | 建 7 个共享任务，写清目标文件、素材路径、验收标准 | 子代理不需要来回问“我该写哪个文件” |
| 写入范围互斥 | 每个任务只允许写 2–3 个固定文件，路径写进任务描述 | 6 路并发零覆盖、零冲突 |
| 七节卡片模板 | 每篇论文固定七节（元信息→结论→动机→机制→实验→局限→启示） | 6 份文档风格一致，合稿几乎不用改 |
| 组首导览 + 组尾对比 | 每组开头一张“文献 / 一句话结论 / 为何入选”表，结尾横向对比 + 5 条落地建议 | 读者可 30 秒判断“这组要不要读” |
| 主控并行产出 | 子代理写精读时，主控写设计总纲（`doc/03`）与索引（`doc/00`） | 关键路径不被“等子代理”阻塞 |

### 4.2 暴露的问题

| 问题 | 现象 | 根因 | 本规范对应条款 |
| --- | --- | --- | --- |
| 素材版本不同步 | 分派时把错的 arXiv 编号写进了某个子代理的素材清单，子代理下载后才发现 | 分派前没有统一做“元信息核验”这一步 | [01 §2](01-检索与相似项目发现规范.md) 检索前先核验标题/作者/编号；[00 §3 阶段 3](00-总览与工作流.md) |
| 子代理理解偏差无法提前发现 | 个别章节初稿把“论文宣称”写成“已实现” | prompt 里只写了“读正文”，没要求分标签 | [02 §4](02-精读与写作规范.md)【宣称 / 代码确认 / 推测】三标签 |
| 返工靠人肉发现 | 初稿个别数字缺表号，靠主控通读才发现 | 没有“数字回源抽检”这个固定关卡 | [02 §3](02-精读与写作规范.md)、[03 §3](03-质检清单与模板.md) |

## 5. 数字与事实核验复盘（本案例最有价值的部分）

### 5.1 核验方法

1. 把 PDF 用 `pdftotext -layout -enc UTF-8` 抽成纯文本，保留表格的列对齐；
2. 对文档里每个“会被引用”的数字，用 grep 回原文找上下文（`Select-String` / `grep -n`），确认单位、条件、表号；
3. 同一数字在多个文档出现时，逐一比对是否一致；
4. 论文宣称的机制，凡涉及 AIOS 的，一律回 `vendor/AIOS` 源码核对。

### 5.3 实际抓到的四类错误（按来源归类）

| # | 错误 | 发现方式 | 处理 | 教训 |
| --- | --- | --- | --- | --- |
| 1 | 二手资料把 arXiv 编号与论文标题张冠李戴（2405.06682 实为 *Self-Reflection in LLM Agents*，正确论文是 2312.03815） | 子代理下载后发现标题不符，回 arXiv API 核实 | 删除错误 PDF、补下正确论文、即时通知受影响子代理 | **任何二手来源的编号/标题，下载前必须回 arXiv API 核验**（`https://export.arxiv.org/api/query?id_list=<id>`） |
| 2 | 论文宣称 AIOS 调度器支持依赖，源码确认 FIFO 调度器不解析子任务依赖 | 阅读 `vendor/AIOS/aios/scheduler/` | 设计改为“应用层 DAG + AIOS syscall”，写入 `doc/03 §3.4.1` | **机制类结论必须落到源码行号**，否则就是转述论文 |
| 3 | RR 调度器 `rr_scheduler.py:181` 在当前代码路径下必崩；FIFO 的 `batch_interval` 默认值是 1.0 s，而注释写 0.1 | 代码库组逐文件读默认值 | 结论定为“只用 FIFO、显式设 `batch_interval`” | **注释不是文档，默认参数以代码为准** |
| 4 | 直接引用“平均加速 1.80×”会误导：LLMCompiler 在 WebShop 上反而变慢（10.72 s vs 5.98 s） | 回原文实验表核对 | 写清“加速有前提：分支可并行且 planner 开销占比低” | **引用加速比必须同时写“什么条件下不加速”** |

## 7. 做对了什么（值得保留）

1. **索引先行**：先写 `doc/00` 的骨架（读什么、为什么读、结论是什么），再让文档填内容，避免“写完了不知道怎么串起来”。
2. **模板约束**：七节卡片 + 组首导览 + 组尾对比，让 6 份精读文档可以当同一本书的章节读。
3. **数字回源**：所有“会被评委追问”的数字都回到 PDF 文本或源码行号，并且把回源方法写进了流程。
4. **互斥写入 + 任务板**：并发写没有一次覆盖事故；任务板同时承担“分工文档”和“进度看板”。
5. **自动化校验**：`build/verify_docs.py` 把“交叉引用是否有效、arXiv 编号与 PDF 是否一一对应、代码块是否配平”变成一次命令，交付前必跑。
6. **主控自己也写**：主控承担设计总纲与索引这两份“最难被替代”的文档，避免变成纯调度员。

## 10. 五条可复用经验 + 交给下一位的三件事

**五条经验**

1. **先定义“相关”，再开始搜**：没有六维相似性定义，检索就退化成“搜关键词前 10 条”。
2. **gold set 是检索的尺子**：赛题点名的 2 篇就是最好的 gold set，用它反推“还缺哪类工作”。
3. **模板比指令更可靠**：给子代理一张七节空卡片，比写 500 字“要深入分析”有效。
4. **数字必须能指到表号/行号**：评委追问时，“论文里写的”不是答案，“Table 3 第 2 行”才是。
5. **复盘要产出条款，不是产出感想**：每条教训都要落到“下次谁在哪个环节做什么”。

**交给下一位的三件事**

1. 读 `doc/00` §2 的 25 篇清单，挑你负责的组，按 [02](02-精读与写作规范.md) 的七节模板补一篇 `doc/1x`；
2. 用 [01](01-检索与相似项目发现规范.md) §7 的 gold set 方法，为你负责的方向补 10 篇候选，并记录检索日志；
