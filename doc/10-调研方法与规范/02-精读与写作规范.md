## 1. 三层阅读法：同一篇论文，读三遍，每遍有硬产出

三层不是"可选的深度"，而是**三个必须完成的检查点**。每层读完必须在论文卡片里落一行文字，不落等于没读；只做速读的论文只能留在候选池"观察"态，**不得写进精读文档**（`doc/00` §7 已把"只读摘要写作"列为禁止项）。

| 层次 | 时间预算 | 读什么（按顺序） | 硬产出 | 读完必须能回答的 3 个问题 |
| --- | --- | --- | --- | --- |
| 速读 | 10 分钟 | 摘要 → 引言最后 2–3 段（贡献清单）→ 所有图表标题（不读图内容）→ 结论 → 相关工作里"我们与它们的区别" | 候选池 3 行判断：值不值得精读 / 属于哪条主线 / 有没有可引用的量化结果 | ① 它把什么问题当成问题（谁的前人做法在哪个环节失效）？② 核心机制一句话是什么（输入→处理→输出）？③ 它最强的一个量化结果是多少、在哪张表？ |
| 精读 | 40–50 分钟 | 方法节逐段（每模块的输入/输出/状态、关键公式、Algorithm 伪代码）→ 实验设置（数据集/模型规模/基线/硬件/并发度）→ 消融 → 失败案例 | 论文卡片 §2.3–§2.6 草稿；每个数字带表号 | ① 机制里真正起作用的变量是哪一个（去掉它结果会怎样，即消融证据）？② 哪个实验能证伪作者的主张（结果反过来时作者会怎么解释）？③ 把结论搬到 7B 端侧，哪个前提最先失效？ |
| 复现性检查 | 10–20 分钟 | 找代码/数据/超参/预算/许可证；核对是否给了 batch、并发、硬件、随机种子；估算最小复现成本（显存、调用次数、依赖） | 卡片 §2.6 的"适用边界"与"最小复现清单" | ① 代码和数据在哪（链接、仓库、附录）？② 最小可复现实验是什么（一条命令或一个脚本）？③ 哪一步在 7B 端侧单卡上不可能复现（显存、70B 基线、专有 API）？ |

**执行规则**：

1. **三层同一天完成**，卡片里记时间戳（如"速读 10:05–10:15 / 精读 10:15–11:00 / 复现检查 11:00–11:15"）。跨天容易把记忆当成原文。
2. **精读必须对照原文**：在 `build/papertext/<arXiv id>-<slug>.txt` 里定位表号再下笔；中文二手解读只能在速读阶段当线索。
3. **速读的三问有一个答不出，就不要进精读队列**——先回摘要补，补不出来说明这篇不该读。
4. **精读三问写进卡片**，尤其第三问（7B 端侧哪个前提失效）——这是本赛题与论文之间最值钱的一句判断；**复现性结论必须可执行**："代码未开源（截至 2026-11-17）"可以，"复现性一般"不行。

**预算参考**：25 篇 ×（10 + 45 + 15）分钟 ≈ 29 人时；不足时按 `10-00` §5.2 裁剪：保点名 2 篇 + 机制/失败/评测各 1 篇，其余降级速读并写明"未覆盖 X，风险 Y"。

## 2. 论文卡片七节模板：每节的合格线

七节名称与顺序固定：论文级用 `## N. 论文名`，七节用 `### N.1`–`### N.7`；论文多时可省略论文级标题，但编号必须连续（`doc/08` 即此写法）。七节是下限，补充小节放七节之后。

### 2.1 元信息

- **目的**：让任何人在 30 秒内找到原文并确认版本，避免"引用了一个不存在的版本"。
- **必填要素**：英文原题；作者与一作机构；arXiv ID + 版本号；发表处（会议/期刊，或"仅 arXiv"）；本地 PDF 路径；抽取文本路径；阅读日期；论文类型（实证 / 愿景 / 综述）。
- **字数参考**：表格 6–10 行，正文 0 字。
- ✅ **合格**：标题 *AIOS: LLM Agent Operating System*；arXiv:2403.16971（COLM 2025，Rutgers）；PDF `doc/papers/2403.16971-AIOS-LLM-Agent-OS.pdf`；文本 `build/papertext/2403.16971-AIOS-LLM-Agent-OS.txt`；2026-11-17 读；类型：实证。
- ❌ **不合格**："AIOS 论文，2024 年，Rutgers 团队的。"——缺 arXiv 编号、缺版本、缺本地文件，无法回源，也无法确认读的是不是同一版。

### 2.2 一句话结论

- **目的**：强迫作者给出"机制 + 量化"的因果句，而不是"提出了一个框架"这种同义反复。
- **必填要素**：≤80 汉字；句式"用【机制】在【设置】上把【指标】从 A 提到 B"；量化必须能回源（表号/章节）；没有实验的愿景/立场论文写"提出了【概念】，但没有任何实验"。
- **字数参考**：≤80 汉字（硬上限）。
- ✅ **合格**："用'先制定计划再逐步求解'的提示替代 Chain-of-Thought 触发句，10 个数据集零样本平均准确率 70.4→76.7（Table 2，text-davinci-003）。"
- ❌ **不合格**："Plan-and-Solve 提出了一种新的提示方法，显著提升了推理效果。"——没有机制、没有数字、没有定位，读完仍不知道它做了什么。

### 2.3 问题与动机

- **目的**：解释"这篇论文为什么必须存在"——前人做法在哪个环节失效、作者的核心假设是什么。
- **必填要素**：前人做法 1–3 条 + 具体失效点（优先带原文数字/图号）；作者的假设一句话；本文与基线的差异是"改变了哪个变量"，不是"更好"。
- **字数参考**：150–300 汉字。
- ✅ **合格**：Zero-shot-CoT 在 GSM8K 的 100 个错误样本中"漏步骤"占 12%、计算错误占 7%（Table 6）；作者据此假设"先做全局规划再执行"能降低漏步骤，把"能力问题"转成"生成顺序问题"（`doc/07` §1.3 即此写法）。
- ❌ **不合格**："现有方法存在不足，本文提出了一种更好的方法。"——哪个不足？有证据吗？改成哪个变量？

### 2.4 核心机制

- **目的**：让没读过原文的队友能复述"数据怎么流动"，并能判断能不能搬进本项目。
- **必填要素**：模块/角色清单（输入、输出、状态）；1 张流程图（mermaid）或编号步骤；关键公式/伪代码位置（Algorithm N、§x.y 或源码行号）；与基线的机制差异（多了/少了哪一步）；关键参数（轮数、并发度、阈值）。
- **字数参考**：300–500 汉字 + 1 张图。
- ✅ **合格**：LLMCompiler 三段流水线——Planner 一次生成带 `$1/$2` 依赖标记的任务 DAG（Fig.2）→ Task Fetching Unit 不调用 LLM，只按"依赖就绪"把任务送进执行器 → Executor 并发执行并回填结果；与 ReAct 的差别是"先编译后执行"，消除了逐步等待（`doc/07` §3.4）。
- ❌ **不合格**："作者设计了一个包含 Planner、Executor 等模块的框架，各模块协同完成并行。"——没有数据流、没有图号、无法判断可搬性。

### 2.5 实验与关键数据

- **目的**：给结论提供可回源的证据，每篇至少 3 个数字。
- **必填要素**：数据集与规模；模型规模（含是否量化）；基线（≥2 个）；关键指标 + 原文表号/图号；加速比/成本/准确率至少 3 个；每个数字带条件；反面结果也要写（如"某任务上更慢"）。
- **字数参考**：300–500 汉字。
- ✅ **合格**：Plan-and-Solve——Table 2 平均 70.4→76.7；Table 5 消融 PS 58.2 vs PS+ 59.3（GSM8K）；Table 6"漏步骤"12%→7% 但"语义误解"停在 27%；模型 text-davinci-003，T=0，10 个数据集。三个以上数字可回源，且给出"哪类错误修不了"的反面边界。
- ❌ **不合格**："实验表明本文方法效果很好，全面超过了基线。"——0 个数字、0 个表号，评委一句"哪张表"就结束。

### 2.6 局限与适用边界

- **目的**：把"不能用的地方"写清；答辩时主动交底，好过被问倒。
- **必填要素**：作者承认的（标【作者承认】+ 章节）+ 我们判断的（标【本文判断】+ 依据）；适用边界至少 3 条（模型规模 / 任务类型 / 硬件 / 数据形态）；指出哪一条对本项目最致命。
- **字数参考**：150–300 汉字。
- ✅ **合格**：Plan-and-Solve——【作者承认】只在 175B 模型上验证（§7）；【本文判断】全文无 7B/8B 数据、无延迟与 token 成本（未报告），迁移到端侧时"先规划"能否被稳定遵循未知；对本项目最致命的是"计划无校验、无回退"。
- ❌ **不合格**："本文方法还有一定局限性，未来可以进一步改进。"——等于没写，且无法据此做技术决策。

### 2.7 对本项目/赛题的启示

- **目的**：把论文结论转成本项目可执行的决策或待验证假设。
- **必填要素**：指向具体对象（赛题 R1–R4 之一、`doc/03` 的某个模块、某个脚本）；给"做法 + 参数 + 验收标准"三件套；不确定的写成"待验证假设 + 验证方法"；**禁止**"很有参考价值""值得借鉴"。
- **字数参考**：150–300 汉字。
- ✅ **合格**："把 PS+ 触发句写入 PlannerAgent 的 system prompt（对应 R2 自动分配）；参数：T=0、计划只生成一次；验收：同一 DAG 校验器下，非法计划（有环/缺 deps）的返工率下降——基线在 `doc/03` 实现阶段实测，本文不预设数值。"
- ❌ **不合格**："这篇论文对本项目很有参考价值，值得借鉴。"——没有对象、没有参数、没有验收，评委无法追问出任何东西。

## 3. 数字引用纪律（本文件最重要的一节）

精读文档被追问最多的问题不是"你懂不懂"，而是"这个数字哪来的、什么条件下测的"。以下 8 条为硬规则，违反任一条按 **P1 缺陷**处理（分级见 `10-03` §5）。

**规则 1：每个对外数字必须标定位。** 粒度到章节 / Table N / Fig.N / Algorithm N / 附录 X；只写"论文里说"不合格。
- 正例：AIOS 无调度总耗时 152.1 s、FIFO 74.2 s、RR 77.3 s（`doc/01` §5.3 的调度消融表）。
- 反例："AIOS 用调度器把速度提升了 2 倍。"——哪个指标、哪张表、什么负载？

**规则 2：必须带条件四件套。** 模型规模（7B/8B/70B/175B/专有 API）、数据集（名称+规模）、硬件（卡型/显存/是否多卡）、batch 与并发度；速度类数字另加**计时口径**（墙钟 / 端到端 / 单请求 / 吞吐）与**统计量**（均值 / 中位数 / p90 / 重复次数）。
- 正例：AIOS 在单卡 RTX A5000 24GB、Llama-3.1-8b + Reflexion、默认 250 线程与 RR 调度下，吞吐最高 2.1×（`doc/01` §5.3；注意这是吞吐而非单请求延迟）。
- 反例："AIOS 快 2.1 倍，所以我们的系统也能快 2.1 倍。"——条件全丢，且把上界当成典型值。

**规则 3：单位与换算必须写清。** 区分"百分点"与"百分比"、"×"与"减少 %"；换算写公式：时间减少 20% ⇔ 加速比 `S = T_serial / T_parallel = 1/(1−0.20) = 1.25×`；反过来，加速比 1.25× ⇔ 时间减少 `1−1/1.25 = 20%`。禁止把"减少 20%"写成"1.2×"。
- 反例："并行后耗时降低 1.25×。"——1.25× 是加速比，不是降幅；这句话在数学上不成立。

**规则 4：原文没报告就写"未报告"，不许推算冒充实测。** 若必须推算，标【推算】+ 公式 + 假设，且与论文数字分栏呈现。
- 正例："Plan-and-Solve 全文未报告延迟与 token 成本，因此不能用来论证加速比。"
- 反例："按每步 2 秒估算，Plan-and-Solve 比基线快 30%。"——这是我们的估算，却被写成了论文结论。

**规则 5：跨论文对比必须同口径，否则写"口径不同，不可比"。** LLMCompiler 的 3.74× 是 Movie Recommendation 任务端到端延迟（8 路并行，GPT）；AIOS 的 2.1× 是 syscall 吞吐（Reflexion + Llama-3.1-8b）。模型、任务、指标三者都不同，不能并列成"一个比另一个快"。
- 正例："两者口径不同（延迟 vs 吞吐、GPT vs 8B），不可直接比较；同口径比较须用 `doc/08` 的基准协议自测。"
- 反例：同一张表里把两个数字放一列比大小。

**规则 6：二手转述不得作为数字来源。** 博客、公众号、中文解读、模型生成的总结只能作为"找论文的线索"；数字必须回 `build/papertext/<id>-<slug>.txt` 或 PDF 原文核对，检索日志里同时留"二手线索 → 一手位置"。

**规则 7：极值与区间必须如实写。** 写"最高 2.1×"就不能写"平均 2.1×"；写"18 个有效格子 13 升 5 平 0 降"就不能写"全面提升"。论文摘要与正文措辞不一致时以正文为准并注明：AIOS 摘要 "2.1× faster execution" 与 4.3 节 "2.1× increase in throughput" 并不严格等价（`doc/01` 译注已指出），引用时写成"吞吐最高 2.1×"。

**规则 8：同一数字全文只能有一个版本。** 合稿时用 grep 全库比对关键数字（如 `2.1`、`152.1`、`74.2`、`3.74`），发现不一致立即回原文核对，并同步"一句话结论 / 正文 / 数据表 / `doc/00` 速查"四处。

## 4. "宣称 vs 实现"标注规则

评委最爱问的一句是"你说是就是？"论文说支持，不等于代码实现了；博客说支持，更不等于。所有涉及**能力 / 机制 / 性能**的陈述必须带标签，标签只有三种：

| 标签 | 含义 | 什么时候用 | 写法要求 | 证据下限 |
| --- | --- | --- | --- | --- |
| 【论文宣称】 | 作者在论文中的主张，未经我们复现 | 引用作者结论、机制描述、论文数字时 | "论文称……（arXiv:ID §x.y / Table N）" | 能指到原文位置 |
| 【代码/复现确认】 | 我们亲自读源码或跑通并留下证据 | 写实现差异、判断可搬性、纠正论文措辞时 | "源码核实：……（文件:行号；运行命令与输出见 `build/notes/…`）" | 能指到文件:行号或命令输出 |
| 【推测】 | 我们的推断、迁移或估计 | 预测本项目效果、解释原因、给设计建议时 | "【推测】……；依据是……；验证方法：……" | 必须给依据与可证伪方式 |

**使用规则**：① 一句话只挂一个标签，混用按 P1 处理；② 顺序固定：先【论文宣称】再【代码/复现确认】，核实可推翻宣称但要保留原文位置；③ 标签用全角【】，同一段不超过 3 处；④ 凡"支持 / 实现了 / 能"的句子都要能追到标签；⑤ 【推测】不得进入 `doc/00` 结论速查。

**本项目实例（AIOS 调度器与依赖约束）**：

- 【论文宣称】AIOS 的调度器集中管理 LLM / Memory / Storage / Tool 四类系统调用队列，并实现 FIFO 与 RR 两种调度算法（`doc/01` §4.3）。
- 【代码/复现确认】源码核实：`vendor/AIOS/aios/scheduler/base.py` 与 `fifo_scheduler.py` 的 `process_llm_requests` 只按到达顺序取批执行，**不解析子任务间的依赖关系**；依赖感知需要在应用层另建 DAGScheduler（`doc/09` §3.3、§3.8；`doc/07` §6.4 亦给出同一判断）。
- 结论写法：**不能**写"AIOS 支持依赖调度，所以直接用它做 DAG"；应写"AIOS 提供队列与 FIFO/RR 机制，**依赖调度由我们在应用层补**（【代码/复现确认】）"。这是把"宣称"当"实现"的典型反面教材。

## 5. 术语统一表

同一概念在一份文档里出现两种译名，评委会认为你没读透；跨文档不一致，会让人怀疑数字也是抄的。规则：① 首次出现写"中文（English）"；② 之后统一用中文；③ 代码标识符、API 名、论文原题保留英文；④ 标题、表格、图标签优先中文，专有名词可保留英文；⑤ 同一文档内禁止混用。

| 英文 | 中文 | 首次出现写法 | 禁用 / 易错写法 |
| --- | --- | --- | --- |
| agent | 智能体 | 智能体（Agent） | 代理、智能代理、AI 代理 |
| multi-agent system | 多智能体系统 | 多智能体系统（multi-agent system, MAS） | 多代理系统、多智能体框架（框架是 framework） |
| orchestrator | 编排器 | 编排器（Orchestrator） | 协调器；不要与调度器混用 |
| scheduler | 调度器 | 调度器（Scheduler） | 与编排器混用（两者分工见下） |
| planner | 规划器 | 规划器（Planner） | 计划器、规划者 |
| context | 上下文 | 上下文（Context） | 语境、上下文窗口（指窗口时写全） |
| context switch | 上下文切换 | 上下文切换（context switch） | 语境切换、上下文转换 |
| syscall | 系统调用 | 系统调用（syscall） | 系统呼叫、系统接口调用 |
| tool | 工具 | 工具（Tool） | 插件（plugin 是另一概念） |
| workflow | 工作流 | 工作流（Workflow） | 流程（process 另有所指） |
| dependency DAG | 依赖有向无环图 | 依赖有向无环图（dependency DAG），后可写 DAG | 依赖图（未强调无环时不要简写） |
| wall-clock time | 墙钟时间 | 墙钟时间（wall-clock time） | 实际时间、真实时间 |
| speedup | 加速比 | 加速比（speedup） | 提速倍数、加速倍数 |
| token | 词元 | 词元（token）；计量场景可写 token | 令牌（指鉴权 token 时才用） |

| baseline | 基线 | 基线（baseline） | 基准（benchmark 专用） |
| fine-tuning | 微调 | 微调（fine-tuning） | 精调、微调训练 |

## 6. 引用格式

**正文引用**：首次出现写"标题简写（arXiv:ID）"，如"LLMCompiler（arXiv:2312.04511）"；再次出现可只写简写；引用具体数字时追加定位："（Table 3）""（§4.3）"。**禁止**裸 URL、禁止只写"某论文"、禁止只写编号不写简写。

**文末文献表**（每份精读文档必须有）：字段固定为 序号 / 作者 / 标题 / 出处 / arXiv 或 DOI / 本地 PDF / 抽取文本。示例一行：

| 3 | Berkeley 等 | An LLM Compiler for Parallel Function Calling | ICML 2024 | arXiv:2312.04511 | `doc/papers/2312.04511-LLMCompiler.pdf` | `build/papertext/2312.04511-LLMCompiler.txt` |

**图片与表格来源**：自绘写"自绘，依据 arXiv:ID §x.y"；转载写"来源：arXiv:ID Table N"；论文截图注明页码。无来源的图表按 P1 处理。

**代码引用**：写 `路径:行号`，如 `aios/scheduler/fifo_scheduler.py:206`（`doc/09` §3.8 已逐行核对）；只写文件名不写行号不合格。

**工程文章引用**：标题 + URL + 抓取日期（本项目统一 2026-11-17），并注明"二手资料，以论文与代码为准"。

**未下载文献**：`doc/00` §2.7 的 arXiv:2505.23885（OWL）与 arXiv:2508.04482（OS Agents 综述）声明未下载，引用时必须写"未下载，仅据摘要/官方仓库"，不得给出表号级引用。

## 7. 横向对比表规范

单篇精读只能证明"我读过"，横向对比才能证明"我判断过"。对比表的必备结构是四列：**维度 | 各系统取值 | 胜出者 | 数据来源**（系统多时中间展开为每个系统一列，但"维度 / 胜出者 / 数据来源"三列不可省）。

**六条规则**：

1. **维度必须可判定且与赛题相关**：分解粒度、依赖表达、并行能力、额外开销、实现复杂度、对本项目适用性。"先进性""创新性"这类不可判定维度禁止出现。
2. **"胜出者"必须填**：具体系统名，或"并列"，或"不可比"；不允许留空。
3. **"数据来源"必须写**：arXiv:ID + 表号/章节；或写"口径不同，不可比"。同一格内不允许混用不同硬件/模型规模的数字。
4. **论文未报告写"未报告"**，不要留空——空会被读成"没查"。
5. **表格下方必须有一句话选型结论**："用 A 的 X + 用 B 的 Y"，不能只有表。
6. **跨组对比表（`doc/00` 层面）只放能同口径比较的维度**；不能同口径就分表，并注明各自口径。

`doc/07` §6.1 的表是可复制的结构样板（维度 × 5 系统 + 一句话选型），但**结构可复制、内容不可复制**：换一组论文必须重新判断。

- ❌ 反例：一张表把"AIOS 2.1×（吞吐，8B）"和"LLMCompiler 3.74×（端到端延迟，GPT）"放在同一列比大小。
- ✅ 正例：分两行两个指标，各带口径，最后写"两者不可直接比较；本项目以端到端墙钟加速比为主指标（`doc/08` 基准协议）"。

> 区分：`10-01` 的相似度评分卡用于**选文**，可有权重与总分；本节的横向对比表用于**支撑结论**，不接受单一总分。

## 8. 文档结构与篇幅

### 8.1 组首导览表

必含列：编号 / 论文 / arXiv 与时间 / 一作单位 / 在主线中的位置 / 对本赛题的关键词。导览表之后接 2–4 段"本组主线"：演进链（谁解决了上一环的什么洞）、共同问题、本组最重要的负面结论。`doc/07` §0 是样板（"分解能力逐级外化"的演进链 + "什么条件下省不了"）。

### 8.2 正文七节

按 §2 顺序，不增删、不改名；补充小节放七节之后。单篇 1500–2000 汉字；`doc/08` 因含 6 篇与基准协议可到全文 15000 汉字上限。

### 8.3 组尾三件套

① 横向对比表（§7）；② **≥5 条落地建议**，每条必须含"做法 + 参数 + 验收"；③ **与 AIOS（`doc/01`）对接表**：我们的组件 | AIOS 对应物 | 对接方式与注意事项。`doc/07` §6.3–§6.4 是样板。

### 8.4 字数与统计口径

汉字数 = `build/verify_docs.py` 的正则 `[\u4e00-\u9fff]` 计数（只统计 `doc/*.md`）。单份文档 8000–15000 汉字；翻译类 `doc/01`、`doc/02` 可超。低于下限说明读得不够；高于上限优先拆表、拆图、拆附录，**不要删证据**。

### 8.5 mermaid 规范

节点 ≤15（理想 6–10）；节点 ID 用 ASCII，标签用中文并加**引号**；避免交叉连线，交叉多就拆图；`flowchart TD/LR` 按阅读方向二选一，交互用 `sequenceDiagram`；每张图后必须有一句"这张图说明什么"；每篇至少 1 张机制图（愿景/综述类可 0 张）。

### 8.6 代码块

必须标语言（`python` / `powershell` / `json` / `markdown` / `text` / `csv` / `mermaid`），不标语言按 P2 处理；命令统一用 PowerShell 语法，路径用 Windows 形式；代码块前后各空一行；代码块内不放大段中文解释（解释写在块外）。

### 8.7 标题层级

每份文档只有一个 `#` 标题；`##` 为章、`###` 为节；不跳级；标题里不用 ✅/🚀 等装饰符号；表格分隔行 `| --- |` 的数量必须与表头列数一致。

### 8.8 文件头与文末

文件头用表格写清：标题 / 适用对象 / 版本 / 日期 / 维护人 / 状态 / 关联文件；文末必须有"相关文件"与"变更记录"两张表（模板见 `10-03` §7g）。
