# 11-同类项目调研与创新空位分析

> **一句话结论**：在 131 个候选项目中，**"多智能体协作 + 任务级并行 + 依赖感知调度 + AIOS 内核/端侧 7B"四者同时具备的项目为 0**。通用编排层（LangGraph/CrewAI/AutoGen）与"Agent OS"品牌层（OpenFang/AOS-CE/elizaOS）已经极度拥挤，**赛题的创新空间不在"再做一个框架"，而在"把依赖感知的任务调度做进 AIOS 应用层，并交付可复现的 7B 实测证据链"**。
>
> - 调研方法：严格按 [doc/10-01 检索与相似项目发现规范](10-调研方法与规范/01-检索与相似项目发现规范.md) 执行（六维相似性、五条路径、两轮检索、0–3 评分卡、gold set 召回评估）。
> - 证据等级：本项目**代码核实** 12 个仓库（本地浅克隆或 `vendor/` 快照），其余为 README/官方文档级证据；每处判断标注【代码核实】/【仅文档】。
> - 本文只解决"别人做了什么、我们还能做什么"；具体实现方案见 [doc/03](03-赛题对标与多智能体系统设计方案.md)，论文依据见 [doc/04](04-智能体操作系统内核与并发服务-精读.md)–[doc/09](09-AIOS与OWL代码库调研与SDK实践.md)。

## 0. 一页速览

### 0.1 六条硬结论

| # | 结论 | 证据强度 |
| --- | --- | --- |
| 1 | **"Agent OS" 已是拥挤的品牌赛道**：OpenFang（18.3k★，Rust 单二进制，自称 kernel/scheduler/RBAC）、AOS-CE（8.5k★）、elizaOS（19.9k★"agentic operating system"）、PhyAgentOS/dimos（具身方向）都在用 OS 叙事，但**没有一个基于 AIOS，也没有一个面向"可并行子任务 + 依赖约束"** | 元数据+README |
| 2 | **没有任何框架实现"自动分解出 ≥4 个可并行子任务并按能力分配给 4 类 agent"**：四个主流框架的分配粒度都停在"下一个谁说话/派给哪个角色"（AutoGen Selector、AgentScope TeamAssign、crewAI manager 委派），LangGraph 根本没有分配层。注意两个**不能误判为已实现**的例外：LangGraph 的 Pregel 有"依赖边→前驱完成即并行触发"的引擎语义，AutoGen 的 GraphFlow 也有（但标注 experimental）；它们给的是**调度机制**，不是**任务分解与能力分配** | 代码核实（`build/notes/frameworks.md` §5、`build/notes/os-frameworks.md` §3） |
| 3 | **通用 DAG 引擎（Airflow/Temporal/n8n/Flyte）证明了拓扑调度可行，但都不懂 LLM**：没有 token 预算、上下文管理、流式输出、模型路由；把它们搬进 AIOS 等于重写 | 元数据+文档 |
| 4 | **最接近我们目标的公开实现是 camel `Workforce`（OWL 的编排实际来自它）+ LangGraph**：camel 有"依赖门控 + 自动派单"，LangGraph 有"依赖边→并行触发 + 并发上限"，但前者不在 AIOS 上、无关键路径优先级、无实测，后者没有任务分配层；**三者拼起来仍缺"AIOS 应用层的依赖感知调度器"** | 代码核实（`build/notes/os-frameworks.md` §2/§3、`build/notes/frameworks.md` §3） |
| 5 | **"串行 vs 并行墙钟时间减少 20%"几乎没有公开对照实验**：LLMCompiler 只有单查询并行（1.80×/3.74×），AgentBench/GAIA/SWE-bench 只测正确率，PilotDeck 的 Workbuddy Bench 测任务成功率——**赛题的加速比协议是空白，做出来就是创新点** | 论文+README |
| 6 | **已有学生/竞赛同类作品集中在"应用层 DAG 编排"**（gitlink 赛题镜像、gitcode"Agent Runtime"高校赛题项目、GitHub 上多个 DAG+ThreadPool 的个人项目），**没有一个落到 AIOS SDK 上，也没有 7B 端侧约束** | 网页+README |

### 0.2 五个创新空位（按"评分贡献 ÷ 实现成本"排序）

| 排序 | 空位 | 为什么是空位 | 对应评分 |
| --- | --- | --- | --- |
| **G1** | **AIOS 应用层的依赖感知调度器（TSU）**：内核只懂 FIFO，DAG 必须在 SDK 侧做 | 已有"依赖门控"（camel `Workforce`，`workforce.py:4491-4493`）与"依赖边触发"（LangGraph Pregel、AutoGen GraphFlow、agentflow），**但没有一个在 AIOS 的应用/请求生命周期里做，也没有"关键路径优先 + 与 1s 攒批对齐 + 7B 实测"的组合** | 效果分 50（≥20% 时间↓）+ 功能分（要求 4） |
| **G2** | **AIOS-SDK 原生的双向协作协议**（`request → feedback → rework` 的类型化消息 + ≥3 对角色闭环） | 通用框架的"反思/批评"是自由文本对话，**没有可验证的闭环状态机**；赛题要求"3 对双向交互"需要可演示、可计数、可断言的协议 | 功能分（要求 3）+ 演示分 |
| **G3** | **端侧 7B 的"并行度 × 攒批"联合调参** | AIOS 的 `batch_interval` 默认 1.0s，与 DAG 并行宽度互相拉扯（并发越高，单批越大，首字节延迟越高），**没有人给出 7B 端侧的联合调参曲线** | 效果分（加速比真实性）+ 答辩差异化 |
| **G4** | **可复现的赛题加速比基准协议** | 现有 benchmark 只测正确率/吞吐；**"串行基线定义、wall-clock 口径、预热、伪加速识别"没人写成规范**（doc/08 §B 已起草，可做成开源 harness） | 效果分 50 + 作品完整度 |
| **G5** | **失败模式护栏（MAST → 检测器 → 重规划）** | MAST 论文只做分类，**没有把 7 类失败映射成运行时检测器并接入 DAG 重规划**；TDAG 只做了子任务改写 | 功能分（正确性 50）+ 稳定性 |

### 0.3 与赛题四条要求的对应

| 赛题要求 | 现有项目覆盖情况 | 我们的差异化 |
| --- | --- | --- |
| ① ≥4 种可协作智能体（AIOS-Agent SDK） | AIOS/OWL 有 agent 抽象，但**没有任何公开项目用 AIOS-SDK 组 4 角色团队** | 4 角色 + SDK 原生实现 + 角色能力矩阵 |
| ② 任务分解 ≥4 个可并行子任务 + 自动分配 | MetaGPT/CAMEL 会分解但**串行执行**；agentflow/Darshit02 有 DAG 但不按"特性"选 agent | Planner 产出带 `agent_type` 的 DAG + 能力匹配分配器 |
| ③ ≥3 对双向交互 | 各框架有"批评/反思"，但**没有类型化闭环与计数** | 类型化 `request/feedback/rework` 协议 + 3 对角色矩阵 + 闭环断言 |
| ④ 依赖顺序与约束 | AIOS 内核**代码中 0 处依赖判断**（见 §5.2） | 应用层 TSU（Task Scheduling Unit）+ 拓扑校验 + 失败重规划 |

## 1. 调研问题与"相似"的定义

### 1.1 第一性问题不是"搜项目"，而是"我们要偷什么"

按 doc/10-01 §1 的要求，先明确本次调研要回答的子问题，再决定检索词：

| 子问题 | 为什么问 | 影响后续哪一步 |
| --- | --- | --- |
| Q1 谁已经在 AIOS 上做多智能体协作？ | 判断赛题是"首创"还是"补缺口" | 决定创新叙事 |
| Q2 谁已经做了"任务级并行 + 依赖调度"？ | 我们的核心创新点是否已被占位 | 决定 G1 的表述 |
| Q3 谁的双向交互/返工协议可以借鉴？ | 赛题硬要求 ③ | 决定协议设计 |
| Q4 谁的评测协议能证明 ≥20%？ | 赛题 50 分 | 决定 benchmark 设计 |
| Q5 谁在 7B 端侧跑通过多智能体？ | 环境硬约束 | 决定降级策略 |

### 1.2 六维相似性（按 doc/10-01 §1.1 口径，权重为本项目设定）

| 维度 | 权重 | 本项目锚点（3 分长什么样） |
| --- | --- | --- |
| 问题定义 | 0.40 | 多智能体在资源受限环境下并行完成可分解任务，且要满足依赖约束 |
| 核心机制 | 0.30 | 代码里有任务 DAG/拓扑调度/依赖等待/按能力分配 |
| 系统架构 | 0.20 | 有 planner / scheduler / executor / memory 分层，且能与 AIOS 映射 |
| 实验场景 | 0.10 | 端侧 7B、并发、真实任务、报告 wall-clock |
| 代码实现 | 系数 k | 3→1.00（可复用）、2→0.95、1→0.90、0→0.85 |
| 技术栈 | 不计分 | Python + Linux 可运行；Rust/TS 需重写的不进精读 |

**强制声明**：权重与 k 系数是经验设定、未经标定（同 doc/10-01 §6.2），只用于排序，不作为"科学结论"。

### 1.3 相关 ≠ 相似 ≠ 同源

- **相关**：同领域但不同问题（如 OSWorld 做 GUI 自动化）→ 观察，不投入精读；
- **相似**：同问题家族且机制可对照（如 AIOS）→ 精读；
- **同源/重命名**：`ruvnet/claude-flow` 与 `ruvnet/ruflo` 是同一仓库改名（stars 均为 81,987），按一条计；`geekan/MetaGPT` → `FoundationAgents/MetaGPT`、`modelscope/agentscope` → `agentscope-ai/agentscope`、`All-Hands-AI/OpenHands` → `OpenHands/OpenHands` 同理。

### 2.5 召回质量评估（doc/10-01 §7）

**Gold set（评审前定义，10 个"必须找到"的项目）**：AIOS、OWL、CAMEL、MetaGPT、AutoGen、ChatDev、AgentScope、LangGraph、CrewAI、TaskWeaver。

| 指标 | 实测 | 说明 |
| --- | --- | --- |
| 关键词路径 Recall@20 | **1/10 = 10%** | 只有 AIOS 进入关键词 Top20；MetaGPT/LangGraph 等因 stars 排序与查询覆盖不足漏掉 |
| 种子/生态路径 Recall@10 | **9/10 = 90%** | 补上 MetaGPT、LangGraph、CrewAI、TaskWeaver 等 |
| 合并 Recall@20 | **10/10 = 100%** | 说明"关键词 + 种子"双路是必要的，单靠关键词会漏掉 90% |
| Precision@20（人工判） | **13/20 ≈ 65%** | 按"是否与本赛题问题/机制相关"人工判定；判为不相关的多为 awesome 清单、无关领域 |
| 各路径独有命中 | 关键词 89 个独有 / 种子 14 个净新增 / 人工 8 个 | 见 `build/recall_eval.py` 输出 |

**诚实记录的三处不足**（对应 doc/10-01 §10.3 的事后复盘要求）：

1. 关键词检索因 403 限流只跑了 6/15 条，**Recall 数字偏低有环境因素**，不能直接当作"关键词路径无用"的结论；
2. 未做 GitHub Code Search（需登录 token），"代码里出现 DAG 调度"类项目可能漏检；
3. 中文生态（gitcode/gitlink）只做了网页检索，未做系统性中文关键词召回。

### 2.6 停止条件

满足 doc/10-01 §5.3 中两条：① 连续两轮新增高相关（S≥1.8）<2 个（第二轮只新增 agentflow/Darshit02 两个）；② 时间预算用尽（本次窗口约 3 小时）。**不承诺"找全"**：GitHub 上每天新增的 agent 项目远超可穷举范围，本文结论限定在"2026-11 时点、五条路径可达范围内"。

### 5.2 机制二：依赖感知调度（核实后重新表述）

**三条经代码核实的事实，必须一起说，否则会被源码打脸：**

1. **AIOS 内核完全不感知依赖**：`aios/syscall/syscall.py:171-186` 入队后直接 `syscall.start(); syscall.join()`；`aios/scheduler/`、`aios/syscall/` 对 `depend|topolog|DAG|predecessor` 零命中（`build/repo_evidence.py` 扫描 167 文件，`build/code_evidence.json`）。**内核不会替我们保序**，依赖只能在应用层实现。
2. **"依赖门控"在应用层已有先例，而且是本项目最需正面回应的竞品**：camel `Workforce` 的 coordinator 产出 `dependencies`（`workforce.py:4011-4040`），调度循环用 `all(dep_id in completed_tasks_info)` 判断前驱全部完成才派发（`workforce.py:4491-4493`）。OWL 的编排完全 import camel，所以"OWL 会依赖调度"实际是 camel 的能力。
3. **"依赖边→前驱完成即触发"的引擎语义也已有成熟实现**：LangGraph Pregel 的 channel 触发（`pregel/_algo.py:470-486`、`_runner.py:485-495`）与并发上限（`_executor.py:143-148`、`_internal/_config.py:221`）；AutoGen GraphFlow 的 `activation_group/activation_condition` all/any（`_digraph_group_chat.py:48/:58`，experimental）；agentflow 的 YAML `needs` + Kahn 分层（`src/scheduler.ts:78-135`）。

**因此 G1 的准确空位表述（修正初稿的过度宣称）**：

> 已有"依赖门控"（camel）与"依赖边触发"（LangGraph/AutoGen/agentflow），但**没有人把"子任务 DAG 调度"做进 AIOS 的应用层**，且现有实现都缺三件事：① **没有关键路径优先级**（就绪即发，谁先谁后不看 critical path）；② **没有与 AIOS 1s 攒批/请求级线程池的对齐与联合调参**（camel/LangGraph 都不在 AIOS 上）；③ **没有任何 7B 端侧的串并行实测数字**（§5.5）。三者叠加才是可交付的创新点。

**注意 AgentScope 的"依赖"不能算调度器**：`Task.blocks/blocked_by` 是数据模型（`state/_task.py:34/:37`），工具说明只写"blockedBy 非空不能领取"（`tool/_task/_list_task.py:38`），**是给 agent 看的约定，不是引擎等待前驱后放行**。

### 5.5 机制五：加速比测量（核实范围：10 个仓库 + 6 篇论文）

## 6. 创新空位：十个候选，五个值得做

> 判定标准：① 现有项目确实没做（有证据）；② 与赛题评分直接相关；③ 我们 2–5 人 × 2 周能做出可信结果；④ 可演示、可度量。**不满足 ③ 的一律标"不建议"**，避免把"宏大的想法"当成创新点。

### G1（主创新）依赖感知的应用层调度器（TSU）

| 项 | 内容 |
| --- | --- |
| 现状 | AIOS 内核 0 处依赖判断【代码核实】；camel `Workforce` 有依赖门控但**不在 AIOS 上、无关键路径优先级、无 7B 调参、无实测数字**（§5.2）；LangGraph/AutoGen GraphFlow/agentflow 有引擎级触发，但都不接入 AIOS 的上下文与批处理 |
| 为什么现有做不到 | 通用框架以"对话/图"为中心，不碰"OS 级请求生命周期"；camel 的 coordinator 依赖 LLM 现场拆任务，无 planner 预产出 DAG 与关键路径；AIOS 官方 SDK 不含 DAG（doc/09） |
| 我们的做法 | Planner 一次产出 DAG（节点含 `agent_type`、`deps`、`est_cost`）→ 应用层 TSU 维护"就绪队列"，按**关键路径优先**派发 → 每节点结束后原子更新依赖计数 → 与 AIOS 的 1s 攒批窗口对齐（小任务合并、大任务抢占） |
| 可验证指标 | 串行 vs 并行 wall-clock 减少 ≥20%（目标 1.3–1.7×）；关键路径利用率；AIOS 请求排队 p90 不上升 |
| 风险 | AIOS 攒批导致"并行反而变慢"（LLMCompiler 的 WebShop 反例：10.72s vs 5.98s，doc/07）→ 必须做"并行宽度阈值"实验 |
| 评分贡献 | 效果分 50 的硬指标 + 功能分要求 ④ |

### G2（主创新）AIOS-SDK 原生的类型化双向协作协议

| 项 | 内容 |
| --- | --- |
| 现状 | 各框架有自由文本反思；无人提供可计数/可断言的双向协议 |
| 为什么现有做不到 | 框架以"对话"为一等公民，不以"任务契约"为一等公民 |
| 我们的做法 | 定义 `TaskRequest / TaskFeedback / TaskRework` 三种消息（JSON Schema）+ 状态机（pending→running→review→rework→done）+ 3 对角色（PM↔Architect、Architect↔Coder、Coder↔QA）的闭环矩阵 + 断言器（每对至少 2 次往返、返工必须引用具体缺陷） |
| 可验证指标 | 3 对双向交互次数 ≥6；返工后缺陷数下降；无死循环（最大轮次） |
| 风险 | 7B 模型生成结构化反馈质量差 → 用模板 + 校验器兜底 |
| 评分贡献 | 功能分要求 ③ + 演示效果 |

### G3（辅创新）端侧 7B 的"并行度 × 攒批"联合调参

| 项 | 内容 |
| --- | --- |
| 现状 | AIOS `batch_interval` 默认 1.0s（doc/09）；无人给联合曲线 |
| 做法 | 固定 4 角色任务，扫 `并行宽度 ∈ {1,2,4}` × `batch_interval ∈ {0.1,0.5,1.0}`，记录 wall-clock/吞吐/p90 等待；产出"端侧甜点区"表 |
| 指标 | 找到 ≥20% 加速的最小改动配置；给出"何时并行无益"的边界条件 |
| 评分贡献 | 效果分的"真实性"论证（答辩时最容易被追问的点） |

### G4（辅创新）可复现的赛题加速比基准协议

| 项 | 内容 |
| --- | --- |
| 现状 | 0 个公开对照（§4.5）；doc/08 §B 已起草 |
| 做法 | 把 doc/08 §B 落成 `bench/` 脚本：串行基线、并发口径、预热 3 次、6 种伪加速检测、日志与报告模板 |
| 指标 | 任意第三方按脚本复现出同量级加速比（±10%） |
| 评分贡献 | 效果分 50 的可信度 + 作品完整度（评委常见追问"你怎么证明不是缓存/预热作弊"） |

### G5（辅创新）失败模式护栏（MAST → 检测器 → 重规划）

| 项 | 内容 |
| --- | --- |
| 现状 | MAST 只做分类（doc/06）；TDAG 只改子任务；无人把 7 类失败做成运行时检测器 |
| 做法 | 对 MAST 的"验证缺口/任务偏离/信息 withholding"等做轻量检测（结构校验 + 交叉检查 + 超时/空输出），命中即触发 TSU 重规划 |
| 指标 | 注入故障实验：级联失败率下降（对照 TDAG 32.61%→4.35%） |
| 评分贡献 | 正确性 50 + 稳定性叙事 |

### G6–G10（不建议单独做，可作点缀）

| 编号 | 想法 | 不建议的理由 |
| --- | --- | --- |
| G6 | 长尾任务动态重规划 | TDAG 已做，且我们时间不够；可并入 G5 |
| G7 | 语义级记忆共享/去重 | AIOS memory 已有基础能力，增量小 |
| G8 | 可视化任务板/时间线 | 是演示加分项，不是创新点；用 2 天做前端即可 |
| G9 | 多模型路由（7B/云端混合） | 赛题环境是端侧单模型，偏题 |
| G10 | "组合创新"叙事 | 必须建立在 G1–G5 的真实结果上，不能空喊 |

**创新点排序结论**：**G1 + G2 为论文级主创新，G3 + G4 + G5 为工程级支撑**。G1 决定"20% 加速"能否成立，G2 决定"协作流程"能否拿满分，G3/G4 决定"结果可不可信"，G5 决定"任务能不能正确完成"。

## 7. 对赛题的落地建议

### 7.1 创新点与评分项的映射

| 评分项 | 分值 | 我们的抓手 | 最小可交付证据 |
| --- | --- | --- | --- |
| 复杂任务合理 | 40/100 | 全栈 Web 应用开发（doc/03 §2） | 任务说明书 + 验收用例 AC1–AC6 |
| 实现与协作流程 | 60/100 | G2 类型化协议 + 4 角色 + 3 对闭环 | 状态机图 + 交互时序图 + 运行日志 |
| **总时间减少 ≥20%** | 50/100 | **G1 TSU + G3 调参 + G4 基准** | 串行/并行对照表（wall-clock，预热 3 次） |
| 正确完成任务 | 50/100 | G5 护栏 + 验收用例 | 通过率 + 失败注入实验 |

### 7.2 与 doc/03 方案的整合（需要改的三处）

1. **§5 调度器**：把"伪代码级 TSU"升级为"关键路径优先 + 依赖计数 + 攒批对齐"三件套，并给出与 AIOS FIFO 的接口（`submit`/`poll`/`wait`）。
2. **§4 双向交互**：把"4 对双向交互矩阵"收窄为**可断言的 3 对**（PM↔Architect、Architect↔Coder、Coder↔QA），每对定义请求/反馈/返工三类消息与最大轮次。
3. **§6 加速来源**：补充"为什么不是伪加速"的三条论证（同模型同 prompt、预热、关键路径对比），并引用 doc/08 §B.4。

### 7.4 "不要做"清单（来自本次调研的教训）

1. **不要宣称"首个 Agent OS"**：OpenFang/AOS-CE/elizaOS 已占位（§4.1）；
2. **不要重写 AIOS 内核**：内核只懂 FIFO，改了也拿不到分，且 RR 调度器有必崩 bug（doc/09 §3.2）；
3. **不要只做 YAML/DAG 编排**：agentflow 已开源同类实现（§4.3）；
4. **不要用"对话轮次"冒充双向交互**：必须类型化、可计数、可断言（§5.4）；
5. **不要用缓存/预热制造加速假象**：doc/08 §B.4 的六条伪加速对策会把自己也筛掉。

## 10. 局限

1. **未运行任何项目**：【代码核实】只表示"源码确有这样的实现"，不等于"端到端行为已验证"；LLM 选人/反馈质量只能靠机制存在性判断，效果需实验（同 `build/notes/frameworks.md` §7）；
2. **"无数字"是仓库内证据**：判定基于 grep（`speedup|wall-clock|faster|latency reduction` 等）与 docs 检索，不排除论文/仓库外博客存在对比数字；
3. **快照时点与完整性**：所有结论对应 2026-11-18 的浅克隆 commit（见两份 notes §0）；crewAI 首轮盘点时工作树未检出，复核后确认完整（999badb，45957 文件），若上游后续变更需重跑；
4. **GitHub 限流**：关键词路径只跑 6/15 条，Recall 10% 有环境偏差；未做 Code Search（需 token）；
5. **中文生态覆盖不足**：gitcode/gitlink 只做网页检索，可能有未公开的同题作品；
6. **Star 数不可作为质量证据**：品牌型项目（OpenFang 18k★）未必有真实调度实现；本文已用"代码核实/仅文档"两档标签区分；
7. **7B 端侧结论部分来自论文外推**：AIOS 原论文用 8B 模型，但未报告"任务 DAG 并行"场景；
8. **权重与阈值未标定**：S 值只用于排序，不构成"科学测量"（同 doc/10-01 §6.2 强制声明）。
